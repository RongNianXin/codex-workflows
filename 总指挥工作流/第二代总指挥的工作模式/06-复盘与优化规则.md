# 复盘与优化规则

## 1. 复盘目的

复盘不是重新规划项目，也不是增加新的管理文档；它只回答一个问题：

> 最近一批任务中，哪些流程可以在不降低执行质量和安全性的前提下变得更短、更准、更自动化？

## 2. 建议的三视角审查

使用者本人、本轮协作成员和其他 AI 的建议均作为候选方案处理。总指挥从工程、程序实现和 AI 执行三个视角做一次合并审查，区分事实、推断、偏好和待确认事项。审查深度与影响相称：简单建议静默检查，不建立三个重复任务或输出三份报告；只有发现会影响结论、范围、风险或执行的问题时才说明。没有证据支持的问题不得为了“对抗式”形式而虚构。

工作流规则的新增、删除或修改默认执行完整闭环：

先区分执行失误、输入/证据不足与规则缺口：已有规则能正确处理时优先纠正执行或补证，不把一次失误自动变成永久规则；明确的系统性、安全或权限缺口无需等待重复发生。新增规则须说明触发范围、可观察收益，以及读取、判断、维护和人工成本，优先替换、合并或澄清原规则。验证通过即停止；实际使用出现无收益、误触发或额外负担时，在下一次相关复盘调整或撤回，不另建评分表或周期记录。

1. 拟定最小修改方案，明确唯一主维护文档、需要保留的安全摘要和验收方式；
2. 修改前对抗式审查目标、团队规范、权限、安全、可执行性、Token、耦合和规则冲突；
3. 根据审查结果修正方案，不把未解决的阻断问题带入文档；
4. 正式修改规则，并记录版本与实际改动；
5. 修改后对抗式复检跨文档一致性、旧规则残留、是否扩大授权、是否误伤正常流程、复杂度和验证结果；发现阻断问题时继续修正后再复检。

使用者本人简述“修改规则”“修改后对抗式审查”等同于授权完成上述低风险本地闭环，不要求其逐步重复确认。若不同修改方向会显著改变目标、远端/生产/不可逆权限、安全边界或团队硬规则，必须在正式修改前暂停并请求决定。简单措辞修正可以静默完成前四步，但不得跳过修改后的最小一致性检查；不得先把有争议的方案落地，再用事后审查为既成事实背书。

## 3. 触发时机

- 一个 Goal 完成或暂停后；
- 集中接管一批 Issue/PR 收口后；
- 连续出现两次以上重复读取、重复任务或无效重试；
- 目标发生重大变化后；
- 交接前；
- 使用者本人主动要求复盘时。

不需要每轮微小操作都复盘。

### 按需时效核验与退役

维护由使用和变化触发，不默认创建定时任务、后台监控、自动联网或独立状态系统：

- 使用时核验：当前动作依赖模型档位、价格、产品界面、API、安装步骤或临时绕过方案时，核对适用版本、官方来源和当前环境；只检查即将使用的内容及其直接依赖。
- 变化时复盘：操作者报告升级、官方更新已进入当前任务，或旧说明实际失效、误触发、与新能力重复时，检查受影响规则。仅知道“有新模型”不触发全仓扫描，也不证明旧方案应被淘汰。
- 维护或发布前核对：对本次修改及 README 中相关时效声明检查来源和依赖；无变化且已有有效证据的不重复联网。用户明确要求一次性全面清查时另定范围，不把轻量交接变成版本审计。

按“声明/规则 → 原用途和依赖 → 当前证据 → 最小处置”判断：仍有效则保留；局部失效则更新；已由现有能力可靠覆盖则合并；确已不适用才退役。官方资料用于核实能力，必要时以当前环境小范围复现判断替代是否成立；链接仍可打开不等于内容仍有效，来源暂不可得只标待确认并暂停依赖动作。新模型的成绩不能替代单写者、授权、安全或专业验收。

退役先核对入站引用、模板、脚本、兼容路径与现有用户依赖。证据不足则保留并标明适用版本；有替代时更新入口并保留必要迁移说明。停用执行规则不等于删除历史证据；不自动删除数据、撤销权限、改远端对象或重写历史。确需破坏性迁移仍走原授权门禁。

复用本次任务记录和已有 CHANGELOG 保存有实质变化的依据、核对日期/适用版本、替代关系、验证与未验证项；公开记录只保留脱敏结论。没有变化不新增记录，不新建全仓时效台账。该机制减少重复检查，但未被使用或触发的内容仍可能过时，不能声称持续监测或始终最新。

模型升级后的“找局限、解决旧难题、拓展功能”按当前目标处理：局限须绑定可复现差距和验收；旧难题保留失败证据与不变量后做最小对照；功能构思只形成有用户价值、代价与验证方式的候选。没有证据支持问题就明确无新增问题；构思不自动转成实现，模型升级也不扩大任务或权限。

本地操作者协作画像已明确启用时，只在重大 Goal、独立里程碑或交接前按 `11-操作者协作画像规范.md` 检查是否出现新的合格证据；更新前先删除到期和无效项、合并重复项并用新证据覆盖旧状态，达到容量上限时不得继续追加。没有新证据就不更新，画像失败也不阻断项目收口。

## 4. 复盘证据

只使用实际可回读的内容：

- 工具调用轮次和失败重试；
- 读取的文档和重复读取次数；
- 任务卡数量、并行波次和等待时间；
- 主窗口与例外专项任务合计的规则载入、证据重复、派发、回执、再汇总和人工转发成本；
- 测试、截图、日志和回执；
- 重型命令、浏览器 worker 数、前台窗口、GPU stall、超时、残留服务和进程归属；
- 人工确认次数；
- 被暂停、取消或替代的任务；
- 发生的状态漂移和重新扫描原因；
- `AI状态索引.md` 中的轮次、任务、授权卡、截点和失败记录。

没有数据时标记“待确认”，不要凭感觉给出精确节省比例。

## 5. 检查清单

复盘只检查本轮实际发生或险些发生的问题；未触发的场景不逐项展开。详细执行标准回到对应主文档：

1. **范围与事实（`02`）**：目标、候选、依赖和排除能否核账；建议、索引和历史是否已回源；是否误纳入弱关联或重复对象。
2. **调度与资源（`02/05`）**：是否坚持单窗口主执行；例外任务是否有净收益；重型步骤是否串行、最小化且可恢复。
3. **工程质量（`02`）**：方案是否满足验收并保持简单；契约、兼容、异常输入、测试和真实根因是否有证据。
4. **授权与安全（`09`）**：本地与远端是否分开；对象、动作、有效期和回执是否精确；是否继承旧授权或绕过硬门禁。
5. **协作交付（`02/09`）**：Review、责任、分支、CI 和交棒是否基于当前 Head 与仓库规则；是否制造无价值 Comment、空提交或重复 Push。
6. **状态与恢复（`04/07/10`）**：唯一事实源、当前行动方、稳定截点、耐久 Commit 台账、`KEY_NODE`、运行身份、决策回执和恢复条件是否可回查；索引是否仍是短指针而非第二套事实库。
7. **效率与材料（`04/05`）**：是否重复读取规则、日志或附件；视觉隔离、会话切换和高成本材料处理是否有净收益，是否把冷存储误写成删除。
8. **收口与简明回执（`02/03/09`）**：计划、执行和平台回执是否分清；遗漏差集是否闭环；必须/建议人工操作是否附步骤、目的、预期结果和异常反馈方式。
9. **协作适配（`11`，仅在已启用时）**：是否只记录跨任务仍有效的抽象协作信息；一次口误、人格评价、身份、项目事实或敏感属性是否被错误写入；易错模式是否有防护动作、过期时间和反例入口。

新建独立任务必须使用 `create_thread`，并在正式工作前完成已授权的最小通信握手；若主动回传失败，应在开工前切换为总指挥只读回收或重建任务，不得等任务完成后才发现无法交接。Office 文件只有在当前对象范围或验收标准明确包含时才处理。任务创建与通信语义以 `04` 为主来源，专项字段以 `03` 为准。

### 高 Token 架构防复发红线

以下任一现象出现即视为流程回归，必须优先简化，而不是继续在其上增加补丁：

1. 总指挥被再次禁止普通实现，导致所有代码、测试、Commit 或远端授权动作都必须经过专项窗口。
2. 默认建立事件 FIFO、Heartbeat、标题同步、收件箱和多份中央视图，并对每个微动作逐层传播同一事实。
3. 使用者需要向总指挥和专项窗口重复描述，或需要人工转发专项结果才能更新项目进度。
4. 为同一根因、同一 PR、同一 worktree、连续 UI 返工或普通局部任务建立多个责任窗口。
5. 只展示总指挥窗口 Token 下降，却不统计专项任务的固定提示、重复取证、等待、回执和再汇总。
6. 为维持调度体系而频繁加载长提示词、全量历史、完整日志或未变化附件。

安全边界不属于可删除的“管理开销”：精确 Base/Head、远端写入确认、未知修改保护、单写者中央状态、完成证据和可靠截点必须保留，但只能在风险和状态真正变化时更新。

## 6. 文档治理

不新建独立“规则的规则”文档。本节是文档治理的唯一主维护位置。

| 文档 | 唯一职责 |
|---|---|
| `00-第二代工作流总览.md` | 架构概览、文档导航与事实优先级摘要 |
| `01-操作者操作手册.md` | 人类入口与可复制提示词 |
| `02-总指挥核心规则.md` | 单窗口主执行内核、路由、净收益门禁与停止条件 |
| `03-专项任务卡模板.md` | 例外专项任务执行契约、任务卡与回传结构 |
| `04-状态、目标变更与交接规范.md` | 状态语义、变化与交接协议 |
| `05-模型选择与资源策略.md` | 模型、Token 与本机资源策略 |
| `06-复盘与优化规则.md` | 复盘、文档治理和流程优化 |
| `07-总指挥交接记录模板.md` | 交接记录结构与接管核验清单 |
| `08-旧版兼容与迁移规范.md` | 可选的旧版兼容与迁移边界 |
| `09-自动化授权与风险分级.md` | 风险、授权和远端写入门禁 |
| `10-自动状态索引规范.md` | 索引位置、字段、检索、回退与持久化 |
| `11-操作者协作画像规范.md` | 可选的本地私有协作画像、有限容量、双重外发确认、过期与隐私门禁 |

修改规则时遵守：

1. 先确定唯一主维护文档；其他文档只保留链接、入口或一句必要安全摘要。
2. 新规则优先并入现有职责，不因内容增加就创建新文件；只有出现独立读者、独立生命周期和独立加载价值时才拆分。
   按需执行手册可以在同时满足这三项时放入 `docs/`，但不得取得新的正式规则编号、产生授权或复制正式门禁；其触发入口、主规则归属和索引方式必须由 00/02/09/10 明确。
3. 操作手册不复制执行算法；任务与交接模板只维护各自契约，不定义新权限；索引不保存第二套项目事实。
4. 安全硬门禁允许简短重复，但详细条件仍回到主维护文档。
5. 每次版本升级前比较变更前后的行数、字节数、跨文件重复和必读文档数量；新增内容必须落入唯一职责，必要镜像要注明主来源。若复杂度增加但执行或安全收益无法证明，撤销或用等量删减抵消。
6. 操作手册面向人类，只保留 AI 无法可靠读取或不能替人决定的输入，并优先使用日常语言；内部状态、算法、ID 和可自动读取的门禁不得转嫁为人工填表。
7. `【】` 只保留操作者实际要选择或填写的规则，不能混入行动规则。开放式作答、多值账号、路径或自然语言限制确实需要帮助理解时，紧跟一个半角括号示例：`【占位符填写规则】(示例：简单、抽象、脱敏的例子)`；纯选择题不加示例。行动规则另起一句。多个同类值默认用逗号分隔；AI 可以兼容顿号或分号并自动规范化。AI 输出模板中的 `【】` 是结构，不要求机械补示例。
8. 面向使用者本人的文档和回答使用日常语言。使用者按编号提出多个问题时，至少提供相同数量的一一对应小节；可以增加必要补充，但不得通过合并问题造成漏答，也不得为了凑小节机械扩写。
9. 私聊中的临时示例、评价性表述和真实项目细节只作为需求输入。公开可复制提示词应抽象为中性、专业、完整、可执行的表达，不逐字引用私聊措辞，不暴露真实人员、项目、路径或内部讨论。AI 仍须接受任意详略的自然语言入口，但不得为了展示容错能力而故意降低公开模板的专业度。

### 专业表达与低操作负担

公开文档以提高交付质量、减少重复操作、明确责任和支持复核为目标。以下是通用产品与文档质量标准，适用于不同领域和经验背景的操作者；公开工作流必须包含完整执行原则，不依赖未分发的私有指令才能保持一致行为。

1. 描述任务、所需输入和可观察结果，不评价操作者的智力、资历或能力；不因输入简短、口语化或表示不确定而降低技术核验标准，也不据此推断人格或专业水平。
2. 专业性来自事实准确、结构清晰、边界明确和可验证结果，不以术语密度、复杂步骤、夸张效果承诺或装饰性措辞代替质量。提供必要技术细节，不把成功率、专业正确性或用户感受写成未经验证的保证。
3. 按“结论与下一步 → 必要操作 → 按需证据”的层次组织；首次使用影响决策的术语时简述实际含义。自动获取能够可靠读取的信息，预填能够确定的参数，保留用户的选择权和结果复核入口。
4. 人工步骤只保留必要决定或 AI 无法完成的观察，并包含操作、目的、成功表现和异常反馈方式。减少人工步骤不减少安全、权限、测试或领域专业验收；AI 的生成结果不得冒充这些验收。
5. 发布前检查：目标与下一动作是否清楚；能否按说明完成操作；失败时能否恢复；必要证据与限制是否可查；是否含对操作者的标签、未核实承诺或来源私聊。发现有依据的问题再修改，不以猜测读者心理无限润色。

公开规则记录可复用的行为要求、适用边界和验收方式；来源材料按已授权的隐私边界处理，仅保留必要内容。私有资料不作为公开工作流的必需依赖，不因文档整改而扩大资料收集或外发范围。

### 高增长文档健康检查

任务每次读取项目进度、当前状态、拓扑、长期任务记录或其他持续增长文档时，静默检查其是否仍适合下一次阅读和交接；不要求每次都改写。文档按性质处理：

- **当前视图**：允许由唯一维护者压缩，保留当前决策所需事实和历史指针。
- **灾难恢复热快照**：与当前视图是同一份活动文档，不另建平行事实库；优先保证空白账号能定位目标、队列、断点、验证、禁止项和下一动作。写入后回读关键字段，终态过程转为冷证据指针。
- **索引**：只保留短摘要、游标和位置，不吸收长正文。
- **人工核验轮次清单**：当前轮次可按问题最小读取；关闭后转冷并默认拒绝回读。中央索引每轮只保存一个清单指针，不展开逐张附件；清单本身不因 Token 优化自动删除。
- **视觉测试包与结果卡**：测试包只保存本轮文字步骤和基线；结果卡只保存逐步骤事实、证据 ID、冲突和最小回读入口。原图留在短寿命观察任务/轮次证据清单，不复制进总指挥热状态或交接正文。
- **唯一任务记录**：保留该任务的目标、关键判断、验证、阻断和交接；终态后可生成短终态摘要，但不能抹去必要证据位置。
- **规则、会议原文、审计账本和原始证据**：不得因变长而被普通任务自动删改；规则修改走本文件规定的闭环，原始材料保持可追溯。

任何带 `保留级别：KEY_NODE` 的提交节点都按 `04` 的耐久台账规则保护。文档精简可以迁移其过程细节，但必须在修改前后核对节点标识、提交映射、保留原因、证据指针和恢复/失效条件；缺一项就不得用精简结果替换旧可靠版本。

压缩触发和具体步骤由 `04-状态、目标变更与交接规范.md` 维护。人工核验每轮结束立即压缩并转冷；附件清理候选按 3 个关闭轮次或 30 天的软触发审查，但不得自动删除。其他文档没有过期、重复、矛盾、终态滞留或交接困难证据时，不做格式化重写；避免把节省下一次读取的收益变成每轮都要支付的维护成本。涉及移动、删除、覆盖历史文件或改变团队共享文档结构时，仍按项目规则取得单独权限。

## 7. 输出格式


## 8. 反思边界

总指挥可以提出改进意见，但不得因为复盘自动修改当前规则、旧版文件或扩大权限。项目代码可按当前 Goal 和有效授权继续处理；工作流规则与授权边界的变更必须形成新版本并由使用者本人确认。
