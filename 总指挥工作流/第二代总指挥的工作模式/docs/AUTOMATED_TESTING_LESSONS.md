# 自动化测试经验与可信结果门禁

版本：2026-09-01.3

定位：本文件是按需加载的自动化测试执行手册，不是新的编号规则，不产生任何授权，也不代替项目测试规范、`02-总指挥核心规则.md`、`05-模型选择与资源策略.md` 或 `09-自动化授权与风险分级.md`。

目的：防止“命令确实运行了，但输入、页面、状态或结果分类错误”被误报成产品失败或成功。测试授权只回答“可不可以运行”；本文件回答“运行结果能不能作为结论”。两道门禁必须分别通过。

本手册负责证明测试装置、输入和结果分类可信；当目标进一步变为定位系统中第一处偏差、验证根因或调优算法时，同时按 `PIPELINE_DIAGNOSIS_AND_ALGORITHM_TUNING_STANDARD.md` 建立实际执行图和因果实验。测试的首个失败阶段是定位证据，不自动等于产品根因。

## 1. 何时必须读取

总指挥自己执行或指挥其他 AI 执行以下任一测试前，完整读取本文件：

1. 浏览器 UI、真实图片、音视频、摄像头、模型推理或 Web Worker 测试；
2. 新旧版本、不同 Commit、不同路由、不同算法或不同配置的对照测试；
3. 无头测试与人工结果冲突，或测试曾出现不稳定、偶发失败、难以复现；
4. 测试会改变镜像、视口、上传媒体、功能开关、缓存、模型状态等产品运行状态；
5. 批量测试、高资源测试或测试结果将用于回滚、替换算法、发布、关闭问题等重要决策。

普通、确定性的单元测试、类型检查和构建不必默认读取；一旦结果冲突、依赖真实运行状态或需要解释有效样本数，立即转入本手册。

## 2. 测试开始前的最小契约

执行者先用短表锁定以下内容；任何关键项无法确认时，先标记 `TEST_INVALID`，不得用测试结果评价产品：

| 项目 | 必须说明 |
|---|---|
| 要回答的问题 | 只写一个可判定问题和成功/失败标准 |
| 对照类型 | 完整产品对完整产品 / 同一产品的核心隔离；不得混用 |
| 版本与入口 | worktree、分支、完整 Head、未提交状态、路由、构建或服务指纹 |
| 输入 | 文件名、SHA-256、尺寸；必要时记录点击点、裁剪框、参数、镜像、视口和功能开关 |
| 就绪条件 | 页面、事件监听、模型、Worker、接口或媒体状态真正可用的可观察信号 |
| 实际系统输入 | 能证明产品实际收到什么的 Worker 请求、裁剪图、结构化诊断或等价证据 |
| 结果来源 | 结构化状态、返回值和页面事实；不得只匹配一条提示文字 |
| 有效分母 | 哪些运行计入成功率，哪些因测试装置错误剔除 |
| 资源与授权 | 是否高资源、worker 数、预计耗时、停止方式和当前有效授权 |
| 证据与清理 | 截图、清单、指纹、日志的保存位置，以及测试后关闭本轮进程的方法 |

对照测试还必须保证除待比较变量外，其余条件一致。无法做到时，把差异列为混杂因素，不能声称因果。

## 3. 固定执行顺序

1. **冻结事实**：核对版本、入口、输入哈希和对照类型。完整旧版本验收与“把旧核心接进当前页面”是两个不同问题，必须分开测试。
2. **等待真正就绪**：不能把 DOM 元素出现、文件输入挂载或页面能打开当作模型、监听器和 Worker 已就绪。优先等待产品提供的稳定状态；没有稳定信号时先补充只读诊断或标记限制。
3. **单样本可见预检**：批量前只跑一个样本，检查上传内容、点击位置、镜像/坐标、实际裁剪、请求阶段和页面结果。无头模式可以继续使用，但必须留下足以还原输入链的证据；必要时用有头模式或截图观察，不能把“看得见”本身当作正确。
4. **通过输入保真门禁**：预期输入与产品实际输入的哈希、尺寸、坐标、裁剪或关键参数一致后，才允许批量。镜像切换、缩放、滚动和覆盖层出现后必须重新核对坐标系。
5. **顺序批量执行**：按项目资源规则使用最低充分并发；高资源默认单进程、单 worker、串行。每轮记录样本、重复次数、开始/结束时间和失败阶段。
6. **结构化分类**：同时读取状态、诊断和用户可见结果，按第 4 节分类；同义成功文案不能被漏计，错误提示也不能被误判成算法已运行。
7. **核对分母与证据**：只用有效运行计算成功率。逐样本清单、输入指纹、阶段、结果和截图数量必须能互相核账。
8. **处理人工冲突**：自动化与人工观察冲突时，先审计测试装置、入口、输入和状态机，再讨论算法。不能先假定人工错，也不能仅凭一次人工成功否定全部自动化证据。操作者看不出结果时记录为 `不确定`，先继续客观核对，不得强迫猜测或把空白当作通过。
9. **结束与清理**：关闭本轮创建且归属明确的服务、浏览器和模型进程；保留最小证据与复现入口，不清理他人进程或未归属成果。

## 4. 统一结果分类

每次运行只进入一个主类别：

| 类别 | 含义 | 是否计入产品成功率 |
|---|---|---|
| `TEST_INVALID` | 测试装置、入口、输入、坐标、就绪或证据不可信 | 否，必须剔除并说明原因 |
| `PRECONDITION_REJECTED` | 产品在算法/Worker 前按规则拒绝输入 | 是，但单独统计，不能写成“检测算法失败” |
| `SYSTEM_ERROR` | 页面、服务、模型、Worker 或接口异常中断 | 是，单独统计 |
| `DETECTOR_FAILED` | 已确认进入目标算法，但没有得到有效识别 | 是 |
| `DETECTED_REVIEW_REQUIRED` | 已识别到结果，但需要人工确认或未生成后续产物 | 是 |
| `DETECTED_CANDIDATE` | 已识别并生成预期后续产物 | 是 |

报告必须同时给出：总尝试数、无效测试数、有效运行数、各主类别数和产品成功率口径。不得把 `TEST_INVALID` 纳入失败率，也不得把前置拒绝冒充算法漏检。

## 5. 已发生过的失败模式与教训

1. **比较对象不等价**：把当前完整页面与旧核心兼容模式比较，随后把结果当成新旧完整版本结论。教训：先锁定“完整产品对照”或“核心隔离实验”，不能混写。
2. **就绪竞态改变输入**：文件输入刚出现就切换镜像或状态，事件监听尚未接管，实际点击被换算到相反位置。教训：记录产品实际收到的坐标和裁剪，单靠自动化脚本中的预期坐标不算证据。
3. **无效批量放大错误**：在输入保真未通过时重复几十次，数量增加却没有增加可信度。教训：一个样本的输入链没通过，禁止放大批量。
4. **按单一文案统计**：解析器只识别一种成功提示，漏掉语义相同的另一种成功状态。教训：优先读取结构化状态；使用文字时必须覆盖状态全集并用人工样本校验分类器。
5. **把前置拒绝算成算法失败**：页面在调用 Worker 前已因区域规则拒绝，却被汇总成检测器漏检。教训：必须记录首个失败阶段和是否实际调用目标算法。
6. **有头模式被误当作可信保证**：能看到页面只提高可观察性，不能证明入口、版本、输入或状态正确。教训：可信度来自完整证据链，不来自浏览器是否可见。

## 6. 停止和升级条件

命中以下任一项，暂停受影响测试，不继续堆样本或调整产品代码：

1. 版本、路由、Head、未提交状态或输入哈希无法锁定；
2. 实际系统输入与预期不一致；
3. 同一脚本重复两次仍出现相同测试装置错误；
4. 结果分类无法区分前置拒绝、系统异常和算法失败；
5. 自动化与人工结论冲突且无法通过现有证据定位差异；
6. 资源消耗超过授权、发生卡顿或出现不归属于本轮的进程；
7. 测试需要新增产品诊断、改变算法、上传外部服务或执行远端写入，但当前授权未覆盖。

停止后只报告：已确认事实、无效原因、受影响结论、最小补救动作和需要的授权，不用无效结果推动回滚、替换或发布。

## 8. 更新原则

只有真实事故具备可回读证据、错误机制已经定位，且教训对多个任务有复用价值时才更新本文件。新增条目应描述通用失败机制、门禁和验证办法，不写个人姓名、项目私有路径、测试素材或一次性日志。正式授权、安全、资源和状态规则仍回到 02、05、09、10；本文件不得静默扩大权限。
