# Pull Request 提交、更新与审查协作标准

版本：2026-09-01.3

定位：本文件是 PR 创建、更新、请求审查、回复意见和准备合并时的按需执行手册。执行内核归 `02-总指挥核心规则.md`，远端权限归 `09-自动化授权与风险分级.md`，加载与状态指纹归 `10-自动状态索引规范.md`。本手册不产生 Push、PR、Comment、Review、Approve、Merge 或其他远端授权。

## 1. 目标与证据模型

PR 的目标不是罗列改过的文件，而是让没有参加口头讨论的审查者能够独立回答：

1. 为什么要改，成功标准是什么；
2. 当前审查的是哪一个 Base、Head、输入和运行条件；
3. 改动范围、数据流和明确未改范围是什么；
4. 实际做过哪些验证，结果是什么，哪些没有验证；
5. 当前风险、专业边界和回退方式是什么；
6. 审查者需要重点判断什么。

同一份代码不自动代表同一套运行系统。依赖、模型、资产、配置、缓存、设备、入口和输入只要可能改变结果，就属于复现基线的一部分。

PR 协作中的三类载体必须分工：

- PR 正文保存当前完整交接契约，是审查者的默认真相入口；范围、实现、验证或风险变化后必须同步更新。
- Review request 或重新请求审查的消息绑定精确当前 Head，说明自上次审查后的增量和本次复核重点。
- Comment/Review 回复记录某条意见的处理过程，不能代替更新已经失真的 PR 正文。

平台的 Required Checks、Review、CODEOWNERS、Auto-merge 和分支保护以当前 Head 的实时状态及仓库现行规则为准。文档中的历史数量、旧批准和旧 Head 不能代签当前状态。

## 2. 加载与适用范围

总指挥在执行以下任一动作前完整读取本手册，并把版本、指纹和加载时间写入项目索引：

1. 创建 Draft 或 Ready PR；
2. 实质更新 PR 正文、Base、范围或交付结论；
3. 首次请求或重新请求 Reviewer；
4. 回复阻断性审查意见；
5. 判断 PR 是否达到可合并状态；
6. 关闭、替代或交接尚未合并的 PR。

仓库模板和贡献规范比本手册更具体时优先执行仓库规则；二者冲突时记录差异，只暂停受影响动作。缺少某项低风险辅助材料不自动阻断其他独立工作。

## 3. 规则分级

- `必须`：所有 PR 都需要，缺失时不得请求正式审查或宣告可合并。
- `条件必填`：仅在对应风险、技术链或仓库规则命中时需要；不适用时写 `N/A` 和简短原因。
- `建议`：有助于审查，但缺失本身不构成合并阻断。

不得把个人写作习惯、固定篇幅、文件数量、测试数量或标题措辞升级为通用硬规则。

## 4. 所有 PR 的必须内容

### 4.1 目的与关联

1. 写明当前问题、期望结果和可观察的成功标准。
2. 关联对应 Issue、决策记录或需求来源。
3. 只有 PR 合入默认分支后能够完整满足 Issue 验收时才使用 `Closes #<NUMBER>`；部分实现、准备、研究或仍有剩余项时使用 `Refs #<NUMBER>`。
4. 纯状态跟踪、长期 owner、开放问题和项目进度留在 Issue；PR 只承载可审查的具体 Diff、实现说明和验证证据；架构或产品取舍按仓库约定进入决策记录。

### 4.2 范围与边界

1. 列出实际改动和用户可见行为。
2. 明确没有修改的相邻功能、公共契约、数据、配置或责任范围。
3. 说明兼容性、迁移、跨模块依赖和可能受影响的队友工作。
4. 一个 PR 默认只承载一个连贯、可独立审查和回退的目标，不用固定行数或文件数判断大小。安全热修可优先拆分；必须原子集成的堆叠或汇总 PR 要补充依赖图、已包含/被替代提交和组合回归结果。

### 4.3 可复现基线

所有 PR 至少记录目标 Base、源分支和请求审查时的精确 Head。以下字段按实际风险条件填写：

- 正式产品入口、操作步骤和关键开关；
- 输入样例、数据版本或脱敏后的内容指纹；
- 运行时、依赖、操作系统、设备或浏览器；
- 模型、权重、资产、配置、profile 和关键参数指纹；
- 缓存、随机种子或会改变结果的状态前提。

精确 Head 不能只依赖会过期的 PR 正文。首次请求和每次重新请求审查时，都必须在请求消息或可审计状态记录中再次绑定当前 Head；Head 变化后旧验证、旧批准和旧审查结论按仓库规则重新判断有效性。

### 4.4 实现与数据流

1. 用短段落说明修改前后的状态或数据流，不复制 Diff。
2. 指出关键文件、公共接口、状态所有权、失败路径和兼容处理。
3. 说明为什么选择当前方案；只有确实影响审查时才列未采用的主要方案。
4. 若命中 `PIPELINE_DIAGNOSIS_AND_ALGORITHM_TUNING_STANDARD.md`，摘要说明实际执行图、第一处可靠偏差、因果实验和最终修改节点。第一处偏差只能作为定位证据；没有受控实验或等价因果证据时，不得在 PR 中写成已确认根因。

### 4.5 验收与失败条件

1. 在报告结果前定义通过条件和明确失败现象。
2. 能客观判断、稳定复现且影响正确性的核心规则进入自动测试或 CI。
3. 视觉、交互、模型和设备效果写明真实入口、输入、操作和人工观察点；自动化、业务接受、独立代码 Review 和专业验收不能互相代签。

### 4.6 实际验证

每项验证同时记录：

1. 命令、入口或输入；
2. 绑定的 Head、配置和必要指纹；
3. 实际结果，包括退出码、通过/失败数量、关键数值或观察结论；
4. 可访问的证据位置；
5. 未运行、失败、跳过和无法判断的项目及原因。

禁止只列命令后写“测试通过”。未运行不能写成通过；模型能加载、程序不报错、静态测试通过和产品效果等价是不同结论。验证日志、截图和附件必须先检查 Secret、个人数据和受监管信息；不得把本地绝对路径、未脱敏材料或内部标识发布到公开仓库。

### 4.7 风险、限制与恢复

1. 写明已知限制、剩余问题、未覆盖输入和结论边界。
2. 行为、数据、配置、依赖、模型或发布风险存在时，给出可执行的回滚、关闭开关或恢复路径。
3. 文档或纯非行为改动没有独立回滚需要时可以写 `N/A：回退该提交即可`。
4. 没有证据时使用“待确认”或“无法评估”，不得写“没有问题”“已稳定”或扩大为专业结论。

### 4.8 审查重点

写明建议 Reviewer、选择依据和需要重点检查的文件、行为、契约或风险。请求多人不表示必须全部批准；最低批准数、CODEOWNERS 和最后 Push 后批准规则以当前仓库事实为准。

## 5. 条件必填证据

| 变更类型 | 额外证据 |
|---|---|
| 文档、注释、非行为整理 | 链接/索引检查、格式检查；其他运行字段可写 `N/A` |
| 行为、接口、配置或数据读写 | 受影响测试、类型/构建、兼容性、异常路径和必要回滚 |
| Bug 修复 | 稳定复现、根因、修复前失败与修复后通过；根因不明或链路复杂时引用链路排查记录，必要时增加反例或 mutation/扰动验证 |
| 重构且声称行为不变 | 等价契约、受影响回归、代表性负例；不能只凭代码相似宣称等价 |
| 视觉、交互、算法或模型 | 同一输入、正式产品入口、模型/资产/profile/配置指纹、关键数值、截图或人工观察、未覆盖设备/样本 |
| 安全、隐私、专业或合规 | 威胁/数据边界、脱敏与最小留存、依据来源、责任方、专业审核状态和不得宣称的范围 |
| 堆叠或汇总 PR | 直接 Base/Head 关系、依赖稳定性、包含/替代映射、组合验证和拆分失败时的恢复路径 |

## 6. 作者提交前门禁

创建或更新远端 PR 前，作者侧必须完成：

1. 回读仓库贡献规范、PR 模板、当前 Base/Head、分支保护、当前 checks、Review/CODEOWNERS 和 Auto-merge；不可访问项标记“待确认”，不引用历史数量替代。
2. 比较 PR 正文与当前 Diff、Commit 列表和实际验证，删除已经失真的说明。
3. 完成当前风险需要的作者侧自修；不能通过降低断言、删除测试、空提交或无意义 Push 清除失败。
4. 检查标题和关联关系。标题描述结果，不写模糊的“update/fix”；`Closes` 与 `Refs` 符合真实完成范围。
5. 检查正文和证据没有 Secret、个人数据、本地绝对路径、内部任务 ID、未经授权的临床或生产保证。
6. AI 可以起草，但 PR 作者必须人工通读最终载荷，并对事实、范围、验证和边界负责。

正文不满足本手册时可以保留 Draft，但不得转 Ready 或请求正式审查。

### 6.1 操作者不记得改动时的发布前恢复

“把当前最新成果推到远端”只表达发布意图，不证明本地所有内容都应进入同一个 PR，也不授权任何远端动作。作者无法列出改动或没有可靠人工验收记录时，AI 必须先执行只读恢复：

1. 保护当前工作区，读取任务记录、当前分支与 worktree、Git Diff、已跟踪未提交、未跟踪和与当前目标有关的忽略项；再核对依赖、配置、模型、资产、生成物和已有验证。不得全量展开缓存、依赖目录、敏感材料或无关忽略项，也不得自动清理、Stash、提交或覆盖来源不明修改。
2. 把内容分为正式候选、无关修改、临时内容和待确认项，逐类写明依据、置信度、是否进入 PR 及保护方式。AI 生成的分类是候选结论，不代替作者对业务范围和人工表现的责任。
3. 优先完成能客观执行的 Diff、构建、测试、配置/依赖/资产一致性和隐私检查。需要人工观察时，准备正确页面、输入和最少步骤，只询问一个可观察现象，并提供 `符合预期`、`不符合预期：【现象】`、`不确定，请继续自动核对`、`未执行` 等可复制选项。
4. 人工状态统一为 `通过 / 失败 / 部分通过 / 未执行 / 不确定 / 不适用`。空白、沉默、未执行和不确定都不能写成通过；只暂停依赖该结论的 Ready、正式审查或合并阶段，其他无依赖核对可以继续。
5. AI 可以替作者核对技术事实，不能替作者编造实际观察、风险接受、隐私决定、专业结论或“已通读最终 PR 正文”。作者无法确认最终载荷时，保留本地草稿或 Draft，并在正文如实记录未验证项。
6. 人工反馈绑定当前 Head、工作区指纹、输入、步骤、观察点、证据和事实时间。绑定事实未变时发布阶段复用；Head、行为、输入链或相关配置实质变化时，只重验受影响项。

最小建议回答：

第一句只有在作者确实完成通读后才能使用；示例不能代替实际操作。

```text
已通读最终 PR 正文和 Files changed，符合预期。
```

或：

```text
我不确定当前范围或人工表现，请保持 Draft，继续自动核对并只把剩余问题交给我选择。
```

## 7. 请求审查与重新请求审查

首次请求或 Head 实质变化后的重新请求使用以下最小格式：

```text
@<REVIEWER>，该 PR 已准备审查。
当前 Head：<FULL_SHA>
目标与范围：<一句话>
实际验证：<命令/入口及结果摘要>
未验证或剩余风险：<无或精确列出>
请重点复核：<文件、行为、契约或边界>
```
同一 Head 不重复刷屏。新 Push 后先更新 PR 正文和验证，再判断是否需要重新请求；只有平台或团队流程需要、旧审查已经失效，或有新的实质信息时才发送新消息。

## 8. 回复审查意见

每条阻断性意见按以下顺序回复：

1. 指向具体意见，明确 `接受 / 部分接受 / 不接受 / 转后续`；
2. 说明修改的文件、行为和原因；
3. 给出新的精确 Head；
4. 报告针对性验证及必要回归的实际结果；
5. 写明仍未验证、保留风险或新建的后续对象；
6. 请求审查者复核明确范围。

```text
@<REVIEWER>，已处理 <REVIEW_LINK> 中的阻断意见。
处理结论：<接受/部分接受/不接受/转后续>
修改：<文件、行为与原因>
当前 Head：<FULL_SHA>
验证：<命令或输入> → <实际结果>
未验证/保留风险：<无或精确列出>
请重点复核：<范围>
```

不同意意见时必须给出可复现证据、契约或当前代码事实，不能只辩解。部分接受或转后续时说明为什么当前 PR 不应扩大范围，并建立可核验的后续承载对象。回复导致 PR 的范围、结果或风险变化时同步修改正文。

## 9. 替代、关闭与交接

PR 被其他 PR 替代或关闭时，说明：

1. 接替对象；
2. 已被包含的精确 Commit、Diff 或功能范围；
3. 尚未包含的独有价值和承载位置；
4. 关闭依据、验证和恢复/重新打开条件。

不得只写“已被替代”。长周期状态、owner 和剩余任务回到 Issue；PR 时间线保留具体交付和审查证据。

## 10. 可合并状态门禁

只有以下条件均满足，才能建议或执行合并：

1. PR 正文与当前 Diff、Base、Head、范围和证据一致；
2. 当前 Head 上平台实时要求的 checks 已满足；checks 为零时已经查明是未触发、等待、跳过还是确无适用工作流；
3. 当前有效 Review、CODEOWNERS、最后 Push 后批准和未解决线程满足仓库规则；
4. 所有阻断意见有闭环，未验证项没有被写成已验证；
5. 需要的人工、设备、专业、安全或隐私门禁已满足，或存在规则允许且如实披露的明确豁免；
6. 没有 Secret、个人数据、内部路径或越权材料；
7. 合并方式、Auto-merge 影响和回退路径已评估；
8. 当前动作取得独立、精确、仍有效的远端授权。

本手册通过只表示 PR 说明和证据契约完整，不产生 Approve、Merge 或 Auto-merge 授权。

## 12. 禁止的低质量模式

以下任一情况都不能作为高质量 PR 交付：

1. 只列文件或功能名称，不说明问题、范围和成功标准；
2. 只粘贴命令，不报告实际结果和未运行项；
3. 把旧 Head 的 checks、批准或截图用于当前 Head；
4. 用“代码相同”推定环境、输入或效果相同；
5. 用模型加载、页面打开或单次成功代替完整效果验收；
6. 把部分实现写成 `Closes`，或把未验证写成已完成；
7. 只在评论中补信息而长期不更新失真的 PR 正文；
8. 为减少 PR 数量混入无关重构、顺手优化或多个独立目标；
9. 固定写死 Required Checks 数量或把个人写作偏好当作仓库硬规则；
10. 发布 Secret、个人数据、本地绝对路径、内部标识或未经授权的专业结论。

```text

Base / 当前 Head：

Closes / Refs 语义：

实时 checks / Review / CODEOWNERS：
平台正文与 Markdown 回读：
远端动作授权与回执：
下一行动方、恢复条件与失效条件：
```
