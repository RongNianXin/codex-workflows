# Pull Request 提交、更新与审查协作标准

版本：2026-09-10.1

定位：本文件是 PR 创建、更新、请求审查、回复意见和准备合并时的按需执行手册。执行内核归 `02-总指挥核心规则.md`，远端权限归 `09-自动化授权与风险分级.md`，加载与状态指纹归 `10-自动状态索引规范.md`。本手册不产生 Push、PR、Comment、Review、Approve、Merge 或其他远端授权。

## 1. 目标与证据模型

PR 的目标不是罗列改过的文件，而是让没有参加口头讨论的审查者能够独立回答：

1. 为什么要改，成功标准是什么；
2. 当前审查的是哪一个 Base、Head、输入和运行条件；
3. 改动范围、数据流和明确未改范围是什么；
4. 实际做过哪些验证，结果是什么，哪些没有验证；
5. 当前风险、专业边界和回退方式是什么；
6. 审查者需要重点判断什么。

同一份代码不自动代表同一套运行系统。依赖、模型、资产、配置、缓存、设备、入口和输入只要可能改变结果，就属于复现基线的一部分。

PR 协作中的三类载体必须分工：

- PR 正文保存当前完整交接契约，是审查者的默认真相入口；范围、实现、验证或风险变化后必须同步更新。
- Review request 或重新请求审查的消息绑定精确当前 Head，说明自上次审查后的增量和本次复核重点。
- Comment/Review 回复记录某条意见的处理过程，不能代替更新已经失真的 PR 正文。

平台的 Required Checks、Review、CODEOWNERS、Auto-merge 和分支保护以当前 Head 的实时状态及仓库现行规则为准。文档中的历史数量、旧批准和旧 Head 不能代签当前状态。

## 2. 加载与适用范围

收到仓库成果的发布或推送请求时，先完整读取本手册，按实际状态使用发布前恢复和交付核验条款；不要求用户提到 PR 或采用特定说法。根据团队规则及目标载体判断是否需要 PR：无需 PR 时，审查请求、PR 正文和合并条款可说明不适用，不能为套模板创建远端对象。只讨论发布方式或引用示例时不执行发布。已有精确授权且仍有效时沿用；目标、载荷或授权不足时只暂停相应动作，不把普通意图当成完整授权。

总指挥在执行以下任一动作前完整读取本手册，并把版本、指纹和加载时间写入项目索引：

1. 创建 Draft 或 Ready PR；
2. 实质更新 PR 正文、Base、范围或交付结论；
3. 首次请求或重新请求 Reviewer；
4. 回复阻断性审查意见；
5. 判断 PR 是否达到可合并状态；
6. 关闭、替代或交接尚未合并的 PR。

仓库模板和贡献规范比本手册更具体时优先执行仓库规则；二者冲突时记录差异，只暂停受影响动作。缺少某项低风险辅助材料不自动阻断其他独立工作。

## 3. 规则分级

- `必须`：所有 PR 都需要，缺失时不得请求正式审查或宣告可合并。
- `条件必填`：仅在对应风险、技术链或仓库规则命中时需要；不适用时写 `N/A` 和简短原因。
- `建议`：有助于审查，但缺失本身不构成合并阻断。

不得把个人写作习惯、固定篇幅、文件数量、测试数量或标题措辞升级为通用硬规则。

### 3.1 发布内容筛选：用途、规则与精确载荷

本节同样适用于无需 PR 的发布准备。AI 先形成有依据的候选，操作者在现行硬规则允许范围内决定精确载荷；筛选通过不等于已授权暂存、Commit 或远端写入。复用现有候选清单，不为每次发布新建制度、必填长表或平台门禁。

1. **先核项目事实与边界。** 分别确认个人/团队协作、公开/私有目标、发布用途、现有目录架构及治理要求，标明用户说明、文档依据、平台查询结果和待确认项。个人项目不自动放宽隐私，团队项目不自动禁止所有素材。没有分支保护不等于没有项目规则；查询失败不等于没有保护。缺少明确约定时，只提出与当前用途相称的最小方案，需新增实质决定时交操作者确认，不虚构 PR 必需性、批准人数、CODEOWNERS 或 Required Checks，也不自行安装这些门禁。
2. **先执行禁止与排除，再判断用途。** 核对仓库规则及操作者本轮明确排除；即使 AI 合成或已有许可，被明确排除的内容仍不纳入。排除项与必要依赖冲突时列为待处置，不用“为了可复现”反向推导上传授权。用途按下表辨认，可同时属于多类，不靠文件扩展名、所在目录或是否已跟踪决定。

| 内容用途 | 候选判断与必要核对 |
| --- | --- |
| 产品源码、脚本、运行配置与资产 | 核实际消费者、入口和交付必要性；必要运行资产应随候选提供或有获准获取方式，不因“只交源码”遗漏。 |
| 可复用测试代码、测试数据 | 团队允许的 fixture 可以是工程交付；分别检查测试代码和数据的用途、规则及依赖，测试依赖不等于产品运行依赖。 |
| 文档、宣传或功能展示素材 | 明确展示位置和受众，符合来源、隐私及授权要求时可列候选；既有公开材料的核验不产生本轮新增公开授权。 |
| 临时截图、日志、冻结运行证据 | 无明确发布用途时保留本地；确需作为交付证据时另核规则、必要性、脱敏及可访问方式，不自动整包附带。 |
| 诊断工具及其内嵌数据 | 只为本次取证、依赖个人目录的工具不默认发布；产品已接入的诊断功能另核必要性，不一刀切删除。 |
| 秘密、受限及来源待确认内容 | 执行相应硬门禁；未知不等于违法，也不等于允许。概括同意不能替代必要依据或覆盖硬禁止项。 |

3. **核内容与副作用。** 源码也可能内嵌像素、个人数据或冻结证据；`.ts`、`.json`、Base64、压缩格式或只保留摘要，都不自动符合排除或隐私要求。检查可移植路径、环境依赖、输出位置及覆盖/清理等副作用；默认只读分析，不为判断用途运行未知诊断工具。最新 worktree 不等于新目录架构获准，沿用团队结构；架构变动另按实际影响定范围。
4. **核依赖是否完整。** 从实际引用、安装/构建与测试入口核对保留和排除后的影响，区分产品运行、维护测试、文档展示与本地取证。需要依赖证据时定点补读，不扫描无关私人目录。不得静默删测试、削断言或隐藏失败来适配排除项。无法同时满足规则和必要交付时，只暂停相关载荷，准备不破坏原成果的最小替代、拆分或获准获取方案，并说明验证缺口；实施涉及新权限时再确认。
5. **核全部待上传内容。** 同时检查最终树与本次将上传的全部提交历史，包括已有未推送提交；不能只检查这次暂存或最后一个提交。`.gitignore` 或后续删除不能消除待上传历史中的内容。已在远端存在、仍在本地历史或仅在工作区分别记录；发现问题保留证据，未经相应授权不清理文件、改写历史、创建新 worktree 或绕过检查。
6. **给可审阅候选。** 在既有清单记录路径或有明确成员的分组、用途、规则/排除依据、必要性与消费者、纳入/排除/待定建议及验证缺口；同类可概括，争议项必须展开。体积、生成物和可重建性按仓库限制与实际获取成本判断，不固定通用大小阈值。操作者无需猜技术字段；最终确认绑定目标、精确文件和历史范围、必要说明及失效条件，不把 AI 分类、旧范围或模板视为确认。

内容筛选不改变后文的分阶段门槛：公开 Draft 仍是公开载荷，不能绕过素材与隐私限制；未取得未来新 Head 的远端检查，不自动构成 Push 前内容筛选失败。实际动作仍按仓库规则、验证范围和当前授权分别决定。

## 4. 所有 PR 的必须内容

### 4.1 目的与关联

1. 写明当前问题、期望结果和可观察的成功标准。
2. 关联对应 Issue、决策记录或需求来源。
3. 只有 PR 合入默认分支后能够完整满足 Issue 验收时才使用 `Closes #<NUMBER>`；部分实现、准备、研究或仍有剩余项时使用 `Refs #<NUMBER>`。
4. 纯状态跟踪、长期 owner、开放问题和项目进度留在 Issue；PR 只承载可审查的具体 Diff、实现说明和验证证据；架构或产品取舍按仓库约定进入决策记录。

### 4.2 范围与边界

1. 列出实际改动和用户可见行为。
2. 明确没有修改的相邻功能、公共契约、数据、配置或责任范围。
3. 说明兼容性、迁移、跨模块依赖和可能受影响的队友工作。
4. 一个 PR 默认只承载一个连贯、可独立审查和回退的目标，不用固定行数或文件数判断大小。安全热修可优先拆分；必须原子集成的堆叠或汇总 PR 要补充依赖图、已包含/被替代提交和组合回归结果。

### 4.3 可复现基线

所有 PR 至少记录目标 Base、源分支和请求审查时的精确 Head。以下字段按实际风险条件填写：

- 正式产品入口、操作步骤和关键开关；
- 输入样例、数据版本或脱敏后的内容指纹；
- 运行时、依赖、操作系统、设备或浏览器；
- 模型、权重、资产、配置、profile 和关键参数指纹；
- 缓存、随机种子或会改变结果的状态前提。

精确 Head 不能只依赖会过期的 PR 正文。首次请求和每次重新请求审查时，都必须在请求消息或可审计状态记录中再次绑定当前 Head；Head 变化后旧验证、旧批准和旧审查结论按仓库规则重新判断有效性。

### 4.3.1 并存实现决议与实际运行身份

同一目标存在多套算法、模块、实验/兼容入口、部署方式、工具链、模型或资产时，PR 作者必须先建立并存实现决议矩阵，而不是只说明本次提交新增了哪个文件：

| 实现或路径 | 用途/责任 | 状态 | 入口与选择器 | 默认/回退 | 本地实际运行 | PR 是否包含 | 验证 | 推荐处置与证据 |
|---|---|---|---|---|---|---|---|---|

1. AI 先从代码、配置优先级、环境变量、构建产物、缓存、进程、部署入口和任务记录恢复矩阵；不得把技术字段转成作者空白问卷，也不得因版本号较大、文件较新或实现被 PR 包含就推定它是默认或实际运行版本。
2. 只有未决选择会改变行为、成本、权限、兼容性或团队责任且现有契约不足以裁决时，才向作者给出少量互斥选项、推荐项、证据和主要代价。作者不确定时继续只读核对；仍需产品或责任决定时保持 Draft，不擅自删除旧实现或切换默认值。
3. PR 正文必须分别记录四项结论：`代码已包含`、`目标环境默认已选择`、`本次验证实际已运行`、`干净环境可复现`。不能用前一项代签后一项；不适用或未确认时逐项说明原因。
4. 人工验收绑定运行身份清单：目标候选、代码基线/工作区指纹、入口和命令、规范启动命令及自检输出、实际 profile/开关/环境覆盖、依赖、模型/资产/配置指纹、服务来源、页面或接口可见版本、核验时间和失效条件。仓库存在规范启动命令时优先使用；没有时由 PR 明确记录等价步骤、选择器和回读方法。自检输出只能证明启动意图和部分前置条件，仍须从已服务资源、诊断端点或页面可见标识证明实际运行身份。只证明页面可打开不能计为目标实现验收。

### 4.3.2 跨机器复现证据

成果身份、未提交增量与四种交付位置的主定义见 [04 成果契约](../04-状态、目标变更与交接规范.md#成果连续性与运行复现契约)。合并后比较实际最终提交/tree及原候选映射，不能机械要求与合并前 HEAD 相等；各层未验证状态不得代签通过。

出现同一代码在不同设备上效果或速度不一致时，按 [链路排查标准“跨机器效果与速度差异对照”](PIPELINE_DIAGNOSIS_AND_ALGORITHM_TUNING_STANDARD.md#跨机器效果与速度差异对照)核对并记录。PR 只需提供各端运行身份、相同输入与操作、首处可靠差异、分段耗时和中间结果的摘要或证据指针，说明已确认原因、仍为假设的因素和未覆盖设备；不能只写“同一 Commit，所以是硬件问题”。

普通 PR 仍按 4.3 的实际影响选取字段，不强制登记无关硬件、模型或性能数据。复现需要但无法取得的参数标为待确认，不用填写齐全的表格冒充实际核验。

本机来源身份与跨机内容一致性分开核验。各端独立确认实际 worktree、进程、服务与目标来源一致；跨端按事先约定比较应相同的代码、资产、配置、输入和语义输出，说明指纹覆盖清单及生成口径。物理路径、进程号、分支标签和硬件可以不同，不以整份本机身份对象全等作为跨机要求，也不伪造路径消除差异。要求同一合并版本时双方绑定其精确提交；不同提交但声称相关内容等价时必须保留内容比较与提交映射，不能跳过核验。

### 4.3.3 接收者能取得并运行的交付

1. 按目标明确支持的环境、实际交付入口与已验证范围；未测设备保持未测，不承诺任意机器一致。不能为了通过验收事后排除原已承诺支持的设备；改变支持范围须按产品和团队约定重新决定。
2. 核对复现所需命令、脚本、依赖锁、配置、样例、模型和资产是否包含在交付候选中，或具有合法可访问的获取方法、版本/校验与必要权限。不能依赖作者未提交文件、私有缓存或只有作者机器存在的路径。受限素材不要求公开，提供获准访问方式或安全替代及证据限制；必要输入无法取得时不宣称接收者可复现。
3. 按实际交付方式验证开发服务、构建产物、预览或部署入口的选择器、资源加载和默认/回退；开发态成功不能代签构建包或生产入口成功。优先复用仓库规范启动及自检，不强制新增容器、安装器或 CI 系统。
4. 分开记录作者现有环境、干净获取环境、另一成员实际环境的证据。影响跨机效果或明确要求成员复现时，必须安排接收方验证并说明负责人、步骤、通过/失败条件；未执行不能写成完成。原始文件相同仍须按测试标准核对实际系统输入，受影响的状态/异步边界不能省略。

### 4.4 实现与数据流

1. 用短段落说明修改前后的状态或数据流，不复制 Diff。
2. 指出关键文件、公共接口、状态所有权、失败路径和兼容处理。
3. 说明为什么选择当前方案；只有确实影响审查时才列未采用的主要方案。
4. 若命中 `PIPELINE_DIAGNOSIS_AND_ALGORITHM_TUNING_STANDARD.md`，摘要说明实际执行图、第一处可靠偏差、因果实验和最终修改节点。第一处偏差只能作为定位证据；没有受控实验或等价因果证据时，不得在 PR 中写成已确认根因。

### 4.5 验收与失败条件

1. 在报告结果前定义通过条件和明确失败现象。
2. 能客观判断、稳定复现且影响正确性的核心规则进入自动测试或 CI。
3. 视觉、交互、模型和设备效果写明真实入口、输入、操作和人工观察点；自动化、业务接受、独立代码 Review 和专业验收不能互相代签。

核心不变量应能由机器客观判定，沿用项目现有测试语言和 CI；不因示例命令改用某种测试框架，也不为普通修改重建流水线。CI 通过只证明已运行检查的覆盖项，不证明所有机器效果一致或临床等专业有效性。真实页面、视觉交互和专业判断仍分别由具备相应责任的人确认。

### 4.6 实际验证

每项验证同时记录：

1. 命令、入口或输入；
2. 绑定的 Head、配置和必要指纹；
3. 实际结果，包括退出码、通过/失败数量、关键数值或观察结论；
4. 可访问的证据位置；
5. 未运行、失败、跳过和无法判断的项目及原因。

禁止只列命令后写“测试通过”。未运行不能写成通过；模型能加载、程序不报错、静态测试通过和产品效果等价是不同结论。验证日志、截图和附件必须先检查 Secret、个人数据和受监管信息；不得把本地绝对路径、未脱敏材料或内部标识发布到公开仓库。

仓库已有的 `npm test`、构建或其他聚合命令仍有基础回归价值，可引用已有操作说明；不能把命令列表当成本次改动的全部验证。每个实质改动或不变契约都要对应具体输入/触发步骤、修改前后预期、失败条件、实际断言或人工观察及证据。使用现有测试即可，不要求每个 PR 新写测试；现有覆盖不足时才补必要用例。沿用测试标准记录全部尝试、有效运行、真实失败、装置无效、重试和退出码采集缺口，不能只取最终通过，也不能把产品失败改称装置无效而剔除。

### 4.7 风险、限制与恢复

1. 写明已知限制、剩余问题、未覆盖输入和结论边界。
2. 行为、数据、配置、依赖、模型或发布风险存在时，给出可执行的回滚、关闭开关或恢复路径。
3. 文档或纯非行为改动没有独立回滚需要时可以写 `N/A：回退该提交即可`。
4. 没有证据时使用“待确认”或“无法评估”，不得写“没有问题”“已稳定”或扩大为专业结论。

### 4.8 审查重点

写明建议 Reviewer、选择依据和需要重点检查的文件、行为、契约或风险。请求多人不表示必须全部批准；最低批准数、CODEOWNERS 和最后 Push 后批准规则以当前仓库事实为准。

## 5. 条件必填证据

| 变更类型 | 额外证据 |
|---|---|
| 文档、注释、非行为整理 | 链接/索引检查、格式检查；其他运行字段可写 `N/A` |
| 行为、接口、配置或数据读写 | 受影响测试、类型/构建、兼容性、异常路径和必要回滚 |
| Bug 修复 | 稳定复现、根因、修复前失败与修复后通过；根因不明或链路复杂时引用链路排查记录，必要时增加反例或 mutation/扰动验证 |
| 重构且声称行为不变 | 等价契约、受影响回归与负例；涉及删除或精简时，按核心规则“行为保持型代码精简”补充可删除性证据、同口径前后收益及恢复路径；不能只凭代码相似或行数下降宣称等价 |
| 视觉、交互、算法或模型 | 同一输入、正式产品入口、模型/资产/profile/配置指纹、关键数值、截图或人工观察、未覆盖设备/样本 |
| 安全、隐私、专业或合规 | 威胁/数据边界、脱敏与最小留存、依据来源、责任方、专业审核状态和不得宣称的范围 |
| 堆叠或汇总 PR | 直接 Base/Head 关系、依赖稳定性、包含/替代映射、组合验证和拆分失败时的恢复路径 |

## 6. 作者提交前门禁

创建或更新远端 PR 前，AI 先完成以下适用技术核对；人工通读按第 6 项的 Draft/Ready 边界处理。每项仍须有效远端授权，Draft 不豁免隐私或硬安全门禁：

1. 回读仓库贡献规范、PR 模板、当前 Base/Head、分支保护、当前 checks、Review/CODEOWNERS 和 Auto-merge；不可访问项标记“待确认”，不引用历史数量替代。
2. 比较 PR 正文与当前 Diff、Commit 列表和实际验证，删除已经失真的说明。
3. 完成当前风险需要的作者侧自修；不能通过降低断言、删除测试、空提交或无意义 Push 清除失败。
4. 检查标题和关联关系。标题描述结果，不写模糊的“update/fix”；`Closes` 与 `Refs` 符合真实完成范围。
5. 检查正文和证据没有 Secret、个人数据、本地绝对路径、内部任务 ID、未经授权的临床或生产保证。
6. 转 Ready、首次请求正式审查前，作者必须人工通读最终载荷。已经通读且正文事实未实质变化时复用；正文范围、验证或风险实质变化后再次通读。尚未通读时只允许本地草稿或已获精确授权的 Draft，不请求正式审查；AI 不代填“已通读”。
7. 命中并存实现条件时，核对决议矩阵和运行身份，确认 PR 没有出现“提交包含实现 A，但本地验收实际运行实现 B”或“干净环境回落到另一默认值”；未决项影响结果时保持 Draft。
8. 按 [3.1 发布内容筛选](#31-发布内容筛选用途规则与精确载荷)核对用途、规则、明确排除、依赖和全部待上传历史；禁限内容未解决时只能保留获准的本地候选，不能借公开 Draft 上传。

正文不满足本手册时可以保留 Draft，但不得转 Ready 或请求正式审查。

### 6.1 操作者不记得改动时的发布前恢复

一般性的发布请求只表达交付意图，不证明本地所有内容都应进入同一载体，也不能单凭该意图补足缺失的远端授权；已锁定具体范围且仍有效的最终确认按 09 核验，不重复索取。作者无法列出改动或没有可靠人工验收记录时，AI 必须先执行只读恢复：

1. 保护当前工作区，读取任务记录、当前分支与 worktree、Git Diff、已跟踪未提交、未跟踪和与当前目标有关的忽略项；再核对依赖、配置、模型、资产、生成物和已有验证。不得全量展开缓存、依赖目录、敏感材料或无关忽略项，也不得自动清理、Stash、提交或覆盖来源不明修改。
2. 把内容分为正式候选、无关修改、临时内容和待确认项，逐类写明依据、置信度、是否进入 PR 及保护方式。AI 生成的分类是候选结论，不代替作者对业务范围和人工表现的责任。
3. 优先完成能客观执行的 Diff、构建、测试、配置/依赖/资产一致性和隐私检查。需要人工观察时，准备正确页面、输入和最少步骤，只询问一个可观察现象，并提供 `符合预期`、`不符合预期：【现象】`、`不确定，请继续自动核对`、`未执行` 等可复制选项。
4. 人工状态统一为 `通过 / 失败 / 部分通过 / 未执行 / 不确定 / 不适用`。空白、沉默、未执行和不确定都不能写成通过；只暂停依赖该结论的 Ready、正式审查或合并阶段，其他无依赖核对可以继续。
5. AI 可以替作者核对技术事实，不能替作者编造实际观察、风险接受、隐私决定、专业结论或“已通读最终 PR 正文”。作者无法确认最终载荷时，保留本地草稿或 Draft，并在正文如实记录未验证项。
6. 人工反馈绑定当前 Head、工作区指纹、输入、步骤、观察点、证据和事实时间。绑定事实未变时发布阶段复用；Head、行为、输入链或相关配置实质变化时，只重验受影响项。

最小建议回答：

第一句只有在作者确实完成通读后才能使用；示例不能代替实际操作。

```text
已通读最终 PR 正文和 Files changed，符合预期。
```

或：

```text
我不确定当前范围或人工表现，请保持 Draft，继续自动核对并只把剩余问题交给我选择。
```

## 7. 请求审查与重新请求审查

首次请求或 Head 实质变化后的重新请求使用以下最小格式：

```text
@<REVIEWER>，该 PR 已准备审查。
当前 Head：<FULL_SHA>
目标与范围：<一句话>
实际验证：<命令/入口及结果摘要>
未验证或剩余风险：<无或精确列出>
请重点复核：<文件、行为、契约或边界>
```
同一 Head 不重复刷屏。新 Push 后先更新 PR 正文和验证，再判断是否需要重新请求；只有平台或团队流程需要、旧审查已经失效，或有新的实质信息时才发送新消息。

## 8. 回复审查意见

**先评估修复影响，再修改和回复。** 审阅意见、CI失败或文本冲突只是触发原因，不降低产品与验证标准。沿用4.3、4.6及[04成果契约](../04-状态、目标变更与交接规范.md#成果连续性与运行复现契约)，在现有证据记录中绑定已认可来源、修复候选及相关未提交增量，区分必须保持的行为、获准改变的行为和已知缺陷。独立判断意见是否成立，不为通过检查而削弱断言、静默改变已认可效果；已证实不安全的行为也不能仅因过去获认可而继续保留，必要变化按当前权限说明影响并取得适用决定。

**按实际改动选择复验。** 代码、配置、输入或组合依赖改变时，只使受影响证据待复验，不机械重跑全部验收，也不沿用已失效的通过结论。纯文档索引修改可做静态检查；共享控制器、容器、状态或接口即使以“修CI”命名，仍须按实际影响核对正例、负例、正式入口及必要人工观察。无法证明影响边界时先扩大分析范围，再确定最小充分验证；检查通过不能代签人工效果或专业结论。

**修复候选与本地开发成果要能对应。** 存在保留未提交修改的开发worktree和隔离发布分支时，先核对单写权、各自基线、相关内容及增量去向，再决定在哪个获准位置修改。能在最新成果上安全修复时优先复用；已在发布分支或远端修过时，先只读核对哪些改动已包含、哪些尚需按意图回纳，不能重复套补丁或覆盖原工作区。不同HEAD不证明产品分叉，指定路径无差异也只证明该范围的Git内容比较，不代签全工程、运行配置或效果一致。保留原基线、恢复指针、排除素材及非发布修改，按3.1筛选干净发布载荷；不得把含排除内容的旧历史带回待上传链。修改、回纳、分支及历史操作仍须在有效本地授权内，检查差异本身不产生实施或远端权限。

每条阻断性意见按以下顺序回复：

1. 指向具体意见，明确 `接受 / 部分接受 / 不接受 / 转后续`；
2. 说明实际修改的文件、行为和原因；有据不接受且无修改时明确“未改代码”及依据；
3. 给出当前精确 Head；没有代码变化无需制造新 Commit；
4. 报告针对性验证及必要回归的实际结果；
5. 写明仍未验证、保留风险或新建的后续对象；
6. 请求审查者复核明确范围。

```text
@<REVIEWER>，已处理 <REVIEW_LINK> 中的阻断意见。
处理结论：<接受/部分接受/不接受/转后续>
修改：<文件、行为与原因>
当前 Head：<FULL_SHA>
验证：<命令或输入> → <实际结果>
未验证/保留风险：<无或精确列出>
请重点复核：<范围>
```

不同意意见时必须给出可复现证据、契约或当前代码事实，不能只辩解。部分接受或转后续时说明为什么当前 PR 不应扩大范围，并建立可核验的后续承载对象。回复导致 PR 的范围、结果或风险变化时同步修改正文。

### 审阅记录的修正与增补

评审记录一旦在远端生效，就是队友会实际看到的协作痕迹。修正它之前必须先完成一次独立对抗式审查（独立性要求见[执行与独立审查](EXECUTION_AND_INDEPENDENT_REVIEW.md)），判定原内容是“不适当”还是“仅缺失”，再按下述分支处置；未经判定不得直接补发。

- **原内容不适当**（结论错误、依据失效、会误导队友、与已核实事实冲突）：整体覆盖。直接编辑那条权威记录的正文，不新增记录；原内容中仍然成立的部分保留在覆盖后的正文里，不因重写丢失证据。
- **原内容仅缺失**（结论仍成立，只是少了说明、证据或边界）：就地增补。保留原文，追加一段带日期的补充说明。默认并入同一条权威记录的正文末尾，避免同一对象出现第二条记录；只有对象不可编辑、平台不支持编辑，或独立成条才符合团队流程时，才另发一条，并在正文首行写明权威条目指向。
- **需要恢复聚合状态**（例如 dismiss 使 `reviewDecision` 丢失）：允许新增记录，但必须先建替代记录、再 dismiss，避免出现没有任何评审意见的空窗；完成后回读确认该 reviewer 的权威条目仍为 1 条。

贯穿全部分支的不变量：

1. 写后必须回读目标对象，只以回读结果为事实；未经回读不得向使用者或队友陈述远端状态。
2. 同一位 reviewer 在同一 PR 上，任何时刻不得存在两条内容相同的权威评审。
3. 不得用追加“改正”已经生效的权威记录；追加只在对象不可编辑，或上述第二、三个分支允许时使用。
4. 编辑覆盖必须打在权威条目（通常是该 reviewer 的最新一条）上；修改非权威条目的正文不会改变聚合状态。
5. 平台能力不同：先判断该对象可编辑、可删除还是只能新增，再套用对应平台的操作清单。已提交的 review 不可删除，只有 pending 状态可删除；dismiss 的权限门槛随仓库设置变化：仅当仓库启用“限制可 dismiss 的人员”时，才限缩到管理员或名单成员，未启用时通常具备写权限即可，执行前按实际设置核对。
6. 结果不确定的远端调用（internal error、超时、连接中断、5xx）在回读确认前按“远端执行待确认”处理，不重复可能造成双写的调用。

单一权威记录优先，是因为平台按每位 reviewer 的最新一条意见计算 `reviewDecision`：重复条目本身不改变聚合结果，却让队友难以判断该以哪条为准；而 dismiss 掉权威条目会连同该 reviewer 更早的意见一起失效。已提交的 review 无法删除，dismiss 事件与时间线记录也无法编辑，因此“不发第二条”的成本远低于事后再收敛。

**优先在 pending 阶段一次成型。** 上述三种处置都是补救，写对一次的成本更低：已提交的 review 不能删除，dismiss 事件和时间线记录也无法编辑，事后收敛只能覆盖或重建，还会在时间线上留下多余条目。因此发起评审时就按最终形态写全结论、依据、边界和请求，避免“先发一条再补一条”；只有确实需要恢复聚合状态时才走上面的重建流程。

## 9. 替代、关闭与交接

PR 被其他 PR 替代或关闭时，说明：

1. 接替对象；
2. 已被包含的精确 Commit、Diff 或功能范围；
3. 尚未包含的独有价值和承载位置；
4. 关闭依据、验证和恢复/重新打开条件。

不得只写“已被替代”。长周期状态、owner 和剩余任务回到 Issue；PR 时间线保留具体交付和审查证据。

## 10. 可合并状态门禁

只有以下条件均满足，才能建议或执行合并：

1. PR 正文与当前 Diff、Base、Head、范围和证据一致；
2. 当前 Head 上平台实时要求的 checks 已满足；checks 为零时已经查明是未触发、等待、跳过还是确无适用工作流；
3. 当前有效 Review、CODEOWNERS、最后 Push 后批准和未解决线程满足仓库规则；
4. 所有阻断意见有闭环，未验证项没有被写成已验证；
5. 需要的人工、设备、专业、安全或隐私门禁已满足，或存在规则允许且如实披露的明确豁免；
6. 没有 Secret、个人数据、内部路径或越权材料；
7. 合并方式、Auto-merge 影响和回退路径已评估；
8. 当前动作取得独立、精确、仍有效的远端授权。

本手册通过只表示 PR 说明和证据契约完整，不产生 Approve、Merge 或 Auto-merge 授权。

### 10.1 合并前验证与合并后复现收口

合并前核验精确 Base/Head 或相应测试合并候选及受影响契约；Base 推进或候选实质变化后重新判断证据有效性。按风险预先安排合并后检查、责任方、验证范围和失败恢复方案。此时实际合并结果尚不存在，状态为待执行，不能要求未来验证先成功才能合并，亦不得绕过已有合并门禁。

合并后读取实际 merge/squash/rebase 结果及对应构建/已服务资源，核对与已测试候选的包含、差异和映射，按风险复测并由接收者验证要求的复现范围。不得用更晚默认分支提交代替本次合并结果，或把 PR Head 的本地结果直接当成默认分支运行证据。仅文档且无运行影响时可做相应静态检查，不强制产品或设备矩阵。

**合并后先核账，再决定本地怎样接续。** 在既有记录中把已认可来源、审阅修复候选、实际合并结果和本地接续目标按精确提交/tree或受影响内容指纹及未提交增量对应起来，复用04的依赖、运行身份和输入证据，不新建第二套长表。物理路径、PID和分支标签可不同；实际相关内容及运行条件一致且证据仍有效时可以复用，缺失的入口或约定成员复现仍标待验证。

本地接续沿用[02共用只读路由](../02-总指挥核心规则.md#发布与同步的共用只读路由)，不把“已合并”解释为必须立即反向合并或执行 `git pull`：内容已包含时不重复移植；内容一致但历史不同仍保留映射，只有后续开发或发布确需历史对齐时才准备相应方案。工作区洁净、祖先关系和目标明确且符合仓库规则时，可在授权内选择仅快进更新；有未提交成果、分叉或重叠改动时，先保护原现场，按实际依赖提出经审阅的整合或隔离验证方案。Fetch、新worktree、同步、Commit及历史变更分别核权限，不默认Reset、Clean、Stash、Rebase或覆盖脏目录。完成后回读目标内容与未提交增量；实际运行和人工验收另行核对。

**出现回归时保全现场，先止损再定位。** 保留最近有证据的良好基线、当前异常现场及已有副作用，暂停受影响交付，明确负责人、下一动作和恢复条件。比较同条件输入下的代码、合并组合、默认值、配置、依赖和缓存，区分原有缺陷与新增回归，不仅凭发生在合并之后就归因于合并。根据影响、可验证性和兼容性选择最小前向修复或获准回退；Revert须核对合并父线、后续提交依赖和数据兼容，代码回退不等于数据恢复。不得用强推或Reset重写公共历史，也不得用CI绿灯掩盖运行差异；部署回退、数据恢复及远端写入必须另有相应授权。

分别报告“已上传”“已审阅”“已合并”“合并结果检查”“本地接续对齐”“交付入口运行身份”“成员复现/未覆盖环境”，未执行、不适用和失败各自说明。合并后 CI 失败、运行身份漂移或复现差异未解决时，只暂停对应成功声明及依赖发布。合并授权不包含自动本地同步、远端回滚、部署或其他写入；修复及恢复按现有权限执行，缺权限只暂停受影响动作。

## 12. 禁止的低质量模式

以下任一情况都不能作为高质量 PR 交付：

1. 只列文件或功能名称，不说明问题、范围和成功标准；
2. 只粘贴命令，不报告实际结果和未运行项；
3. 把旧 Head 的 checks、批准或截图用于当前 Head；
4. 用“代码相同”推定环境、输入或效果相同；
5. 用模型加载、页面打开或单次成功代替完整效果验收；
6. 把部分实现写成 `Closes`，或把未验证写成已完成；
7. 只在评论中补信息而长期不更新失真的 PR 正文；
8. 为减少 PR 数量混入无关重构、顺手优化或多个独立目标；
9. 固定写死 Required Checks 数量或把个人写作偏好当作仓库硬规则；
10. 发布 Secret、个人数据、本地绝对路径、内部标识或未经授权的专业结论。
11. PR 只提交某套实现，却不核对默认值、回退、环境覆盖、缓存和旧进程，导致本地验收实际运行另一套实现。
12. 把“版本号最大”“最近 Commit”“文件已存在”或“页面能打开”直接写成当前最新可靠成果或效果一致。
