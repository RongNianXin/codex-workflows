# 傻瓜式同步当前项目到远端仓库

## 最简单的用法

如果本地已经配置过远端仓库，只需发送：

```text
请把我当前项目的最新修改安全同步到远端仓库，并在验证通过后完成合并。
```

如果尚未配置远端仓库，只需多提供一个地址：

```text
请把我当前项目的最新修改安全同步到这个远端仓库，并在验证通过后完成合并：<远端仓库地址>
```

使用者不需要知道本地分支、远端分支、临时分支、合并方式、测试命令或冲突处理方法。这些都由 AI 根据当前项目自动识别和判断。只有缺少登录、Git 作者信息，或者冲突确实无法根据代码和测试判断时，AI 才应向使用者提问。

## 完整提示词

如果希望把执行要求也一并交给 AI，可直接复制下面整段；通常只需替换远端仓库地址，本地已经配置好远端时可以删除地址这一行。

```text
请把我当前项目的最新修改安全同步到远端仓库，并在验证通过后完成合并。

远端仓库地址：<可选；如果当前项目已经配置正确的远端仓库，就自动读取，不要再问我>

请自动完成必要的专业判断，不要要求我填写或解释 Git 分支、默认分支、临时分支、合并策略、验证命令、冲突规则等技术参数。

请从当前任务正在处理的本地项目开始，先读取项目规则，再自动识别仓库根目录、当前分支、默认分支、远端地址、登录账号、工作区改动、未跟踪文件、本地提交、远端新增提交、分支保护和可用的测试命令。如果缺少非关键参数，优先依据仓库现状和通用安全原则继续，不要把专业判断转交给我。

如果只有本地发生变化，就整理本地改动、运行检查并提交；如果远端也新增了提交，就先获取远端最新状态，再根据真实提交关系选择安全的整合方式。只有确有必要时才创建临时分支或 worktree，不要为了流程形式增加复杂步骤。

当本地和远端修改重叠时，请逐个检查冲突文件、相关提交、调用关系和测试结果。能够明确判断的冲突由你自动解决，同时保留两边兼容的有效改动；不得机械地整文件选择本地版本或远端版本，也不得仅按修改时间判断。只有不同方案会明显改变功能、数据或兼容性，而且现有证据不足以判断时，才用通俗语言一次性向我说明选项和影响。

必须保护当前工作区和现有修改：不得使用 reset --hard、clean、强制检出、强推或其他可能丢失内容的操作；不得覆盖来源不明的修改；不得上传 .gitignore 已忽略的内容、凭据、敏感资料、个人路径或与本次更新无关的文件。只处理为完成本次同步所必需的内容。

提交前自动运行项目现有的测试、构建、静态检查、链接检查和敏感信息检查；项目没有完整测试时，执行能够找到的最接近验证，并明确说明未验证部分。测试失败时先判断是否由本次改动导致，不能把未运行或无效的测试说成已经通过。

本指令授权你在指定仓库范围内执行必要的本地 Commit、创建工作分支、Push、创建或更新 PR、查看检查结果并处理本次改动造成的问题。如果仓库只有我一人维护，而且仓库规则和平台权限允许，可以在检查通过后自审并合并，再删除本次远端工作分支并同步本地默认分支；如果存在其他协作者、强制人工审核、登录、验证码、权限不足或平台明确要求人工确认，就推进到实际阻断处再告诉我最少需要做什么。不得强推、修改仓库权限或设置、绕过分支保护，也不得处理本次范围之外的 PR、Issue 或分支。

执行结束后，用简短清单告诉我：同步了哪些内容、如何处理本地与远端差异、测试结果、远端提交或 PR 链接、是否已经合并，以及仍需注意的风险。不要只给我操作教程；在权限允许的范围内直接执行到底。
```

## 设计原则

- 用户只描述目标，不负责选择 Git 技术方案。
- AI 优先自动识别和继续执行，只有真正影响结果的歧义才提问。
- 简单情况走简单流程；只有本地与远端同时产生复杂改动时，才启用临时分支或 worktree。
- 自动化不等于跳过安全检查，也不等于可以覆盖本地修改或绕过远端规则。
