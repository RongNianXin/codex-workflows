## 一、文档目的

本文根据两类已脱敏的长任务断联案例整理，目标是解决两个长期问题：

1. 使用 CC Switch 切换账号或中转站后，借助项目状态记录或交接快照可靠恢复任务进度；这不承诺原聊天历史或隐藏 reasoning 状态可以跨 Provider 兼容。
2. 再遇到 401、模型不支持 404、502、503、504 时，可以快速判断是账号、模型映射、上游、网络、代理还是任务历史问题，不必每次临时让 AI 从头调查。

本文不要求放弃 CC Switch。CC Switch 仍适合统一管理账号和一键切换；需要改变的是长任务的状态管理和切换方法。

## 二、两类案例的已确认事实

### 1. 故障并非单纯“额度不足”

本次先后出现了两类不同故障：

- 旧 provider 返回 `401 Invalid API key`，说明该凭据已被上游拒绝。
- 原长任务后续的关键错误为：

```text
input[17].encrypted_content missing_required_parameter
```

第二类错误是 Responses 历史重放或代理转换时缺少必需字段，不是典型的额度耗尽提示。

第三方中转可能重新包装状态码，因此不能只看 `401`、`502` 等数字；必须同时看错误正文里的 `cause`、`upstream_status` 和参数名称。

### 2. 本地会话文件没有发现对应字段损坏

离线检查结果：

- 会话文件规模较大，包含多轮 JSONL 历史。
- 成功请求包含较长的输入历史和多次上下文 compaction。
- 已抽查的顶层 reasoning item 均有非空 `encrypted_content`。
- 最新 compaction replacement history 也保留了加密内容。

因此，现有证据不支持“磁盘 JSONL 本体丢字段”。更可能的故障位置是失败回合 rollback 之后的请求组装、历史裁剪或 CC Switch / 上游的格式转换层。

### 3. 直接换中转站不能修复结构化历史错误

如果原线程已经在失败回合中形成不兼容或不完整的请求历史，切换到另一个健康 provider 后，原线程仍可能继续发送同一份坏请求。本节只解释包含密文、字段转换或分页谱系信息的结构化错误，不适用于只显示上游暂时不可用的纯 502。

这解释了为什么：

- 新建短对话可以回复。
- 旧的长任务仍然失败。
- 再换一个中转站也不一定恢复。

### 4. 历史案例曾用 Fork 绕开失败活动回合

案例中从原任务建立了同目录 fork：

```text
<FORK_TASK_ID>
```

恢复任务只继承已经完成的历史，不包含失败中的活动回合。只读恢复握手成功，并正确复述了既有断点，没有再次出现 502 或 `encrypted_content` 错误。

这只证明 Fork 在该案例中绕开了失败活动回合，不能把它推广成默认恢复方式。当前规则要求先从项目现有状态记录或交接快照恢复；只有操作者明确要求继承源任务的已完成聊天历史时，才使用 Fork。

### 5. 纯上游 502 是另一类故障

后续案例的错误正文没有字段缺失、transform 或分页谱系信息，而是：

```text
unexpected status 502 Bad Gateway: CC Switch local proxy failed while handling Codex endpoint /responses. Provider: <PROVIDER_A>; model: <SOL_MODEL>; upstream_status: HTTP 502; cause: Upstream service temporarily unavailable, url: http://127.0.0.1:<PORT>/v1/responses
```

其中 `127.0.0.1:<PORT>` 是用户电脑上的 CC Switch 本地代理地址，不是中转站服务器地址。该错误只证明 CC Switch 转发 `/responses` 时收到或生成了上游 502；客户端证据不能继续区分账号池、调度节点、认证刷新、容量、超时或协议转换中的哪一项失败。

日志显示，真实长任务先成功读取材料和执行部分工具，下一轮 `/responses` 才报 502。多数同类 502 很快返回且没有输入、输出 Token；同一时间段前后也存在成功请求。这与“上游短时不可用或调度失败”一致，但最终根因仍需要中转站服务端日志确认。

### 6. 502 后的同一时段对照

案例中 CC Switch 自动故障转移始终关闭，因此下列请求没有被自动切换到其他备用 Provider。一次 502 复现后，在较短时间内进行了以下只读对照：

| 对照 | 结果 | 能说明什么 | 不能说明什么 |
| --- | --- | --- | --- |
| Provider A，干净窗口，固定文本 | 成功 | 账号和代理没有持续失效 | 复杂请求已经恢复 |
| Provider A，干净窗口，一次工具及结果续轮 | 成功 | 基础工具续轮可用 | 所有工具链和长上下文都可用 |
| Provider A，原长任务窗口，固定文本 | 成功 | 原线程没有永久损坏 | 原复杂任务再次执行一定成功 |
| Provider B，固定文本及工具续轮 | 成功，但模型档位不同 | 另一条中转链路当时可用 | 与 Provider A 构成严格同模型对照 |
| Provider B，同一复杂任务 | 使用相同模型家族成功完成 | 任务复杂度本身不是充分触发条件 | 两个 Provider 的账号池和节点完全相同 |

另一个独立的复杂任务在 Provider A、同一 Sol 模型和极高推理设置下连续运行约 10 分钟并完整成功。这个结果进一步说明，运行时间、任务复杂度或极高推理本身都不是 502 的充分条件。

这组证据推翻了两个过强判断：

1. 不能因为干净探针成功，就直接认定原线程历史损坏。
2. 不能因为复杂长任务曾失败，就认定长任务、工具调用或高推理必然触发 502。

更谨慎的结论是：Provider A 的 502 具有间歇性；长任务请求次数更多，可能更容易撞上短时故障，但它只是风险放大因素，尚未证明是根因。

### 7. Astra 404 与 Sol 502 必须分开

Provider A 使用 Astra 的多个推理档位时，均返回：

```text
unexpected status 404 Not Found: CC Switch local proxy failed while handling Codex endpoint /responses. Provider: <PROVIDER_A>; model: <ASTRA_MODEL>; upstream_status: HTTP 404; cause: Model "<ASTRA_MODEL>" is not supported by any configured account in this group, url: http://127.0.0.1:<PORT>/v1/responses
```

切回 Sol 后，同一账号和同一任务窗口可以继续响应。Provider B 则能使用 Astra 完成长回复，并在 5 个独立窗口中分别完成后述 P1～P5。因此：

- Astra 404 已明确指向 Provider A 的账号组或模型映射不支持该模型；改变推理等级无效。
- Sol 502 是间歇性的上游可用性问题，当前没有唯一根因。
- 两种错误的状态码、`cause` 和修复责任不同，不能合并为“模型太复杂”或“CC Switch 不支持 Astra”。

### 8. `model_provider = custom` 不是充分根因

案例中，发生 502 的中转配置与稳定使用的官方账号配置都曾使用 `custom`。仅凭这个字段无法解释为什么一条线路间歇失败、另一条线路稳定。总路由开关还会改变实际数据路径，所以比较配置时必须同时记录请求是否经过 CC Switch 本地路由、目标地址、模型映射和账号组，不能只比较 `custom` / `OpenAI` 标签。

### 9. 回滚后错误消失不证明回滚修复了 502

历史迁移回滚可以撤销会话文件或分页谱系改动，因此能够解释迁移后出现的结构化红色错误为什么消失；它不能修复中转站上游短时不可用。回滚后 502 同时消失，可能只是上游在操作期间恢复、客户端重新发起了新请求，或线路状态发生变化。没有回滚前后同一请求和服务端日志，不能建立因果关系。

## 三、这次最重要的经验教训

### 1. 短消息成功不等于长任务链路健康

发送“你好”会创建新的 `/responses` 请求，可能继续原任务并写入新的会话状态，因此它不是无副作用的只读探针。若已经发送成功，它最多只能证明：

- 当前账号可以完成一个短请求。
- 当前网络和代理并非完全不可用。

它不能证明：

- 长时间流式连接不会断开。
- 多轮 reasoning 历史可以继续重放。
- 工具调用和工具结果格式兼容。
- 上下文压缩后的密文可以跨 provider 使用。
- 当前额度足以支持一次高 reasoning 的长任务。

### 2. “历史列表统一”和“历史可跨账号继续”不是一回事

CC Switch 的统一历史功能可以让不同来源的任务出现在同一个列表中，但不等于它能把 provider A 生成的加密 reasoning 状态转换成 provider B 可用的状态。

普通聊天文字通常可移植，`encrypted_content`、服务端 response ID、compaction 状态可能和原账号或原上游有关。

### 3. 长任务不能只依赖聊天窗口保存状态

会话上下文属于易失状态。账号、provider、代理、模型、compaction 或失败回滚任一环节变化，都可能让隐藏历史无法继续。

真正可靠的任务状态必须落在项目文件中，至少包括：

- 目标和验收标准。
- 已确认事实与关键决策。
- 已修改文件和当前 Git 状态。
- 已执行的测试及结果。
- 未完成项、风险和下一步。

### 4. 并行恢复可以，双写同一 worktree 不可以

可以让一个任务继续产品开发，同时让另一个任务只读调查会话故障；但两个任务不能同时修改同一个工作目录。

接管时必须明确“唯一写入者”，旧任务暂停后，新任务才能继续修改。

### 5. 连续点击重试可能让现场更复杂

对于普通瞬时网络故障，有限重试是合理的；但对于以下结构化错误，重复原请求通常没有意义：

```text
encrypted_content missing_required_parameter
Encrypted content could not be verified
transform error
validation error
phase missing
```

失败回合还可能不断 rollback，增加定位难度。此时应保留原任务作为审计现场，先从项目已有状态记录或交接快照恢复。只有操作者明确要求继承已完成聊天历史时，才从源任务 Fork。

### 6. “你好”成功不是恢复验收

短消息可能让客户端读取上一轮未完成任务并继续执行，而不是创建一条与旧任务无关的请求。它随后再次报错也不矛盾：一次长任务会产生多轮 `/responses` 请求，某一轮成功不能保证后续轮次成功。诊断时应使用下文定义的固定探针，并记录每次请求发生在首次响应、工具调用前后还是输出过程中。

### 7. 中转比官方直连慢需要定量对照

中转链路通常比官方直连多出本地代理、中转服务器、账号调度、协议转换或重试，因此“体感更慢”在结构上合理。但没有同一时段、同一模型、同一提示词的 A/B 计时，只能记录为观察，不能声称具体慢多少或已定位到某个环节。

### 8. 客户端重连次数不等于人工重试次数

案例环境中，CC Switch 自身存在有限重试，Codex 客户端还会显示“重新连接 5/5”。一次用户操作可能因此产生多次上游请求。服务端日志中连续出现多条 502，不应直接解释成用户手动重复发送了同样数量的请求。排查时应同时记录客户端回合、CC Switch 重试设置和服务端请求 ID，按请求链归组。

## 四、以后长任务的标准状态管理

优先使用项目已经建立的任务状态或交接机制，不要再复制一套事实库。项目没有任何可靠记录、且任务确实较长时，可以使用以下三份文件作为一种实现：

```text
task_plan.md
findings.md
progress.md
```

用途分别是：

| 文件 | 内容 |
| --- | --- |
| `task_plan.md` | 目标、阶段、边界、验收标准、当前状态 |
| `findings.md` | 已确认事实、根因、关键决策、外部资料 |
| `progress.md` | 实际改动、验证结果、未完成项、下一步 |

以下时点应更新项目实际采用的状态机制：

1. 完成一个阶段后。
2. 执行高风险或耗时操作前。
3. 切换账号、provider、模型或中转站前。
4. 上下文即将压缩或任务已经很长时。
5. 准备把任务移交给另一个窗口时。

代码任务还应记录：

```powershell
git status --short
git diff --stat
```

不要把未经提交的代码是否存在、测试是否通过等关键信息只留在聊天文字里。

## 五、切换账号或中转站的安全流程

### 切换前

1. 等待当前回复完成，确认没有工具或终端命令仍在运行。
2. 让当前任务更新项目已有的状态或交接机制；项目没有可靠机制且任务确实较长时，再补充 `task_plan.md`、`findings.md`、`progress.md`。
3. 记录 Git 状态、测试结果、未完成项和下一步。
4. 生成可直接交给新窗口的续接提示词或交接快照；只有操作者明确要求继承已完成聊天历史时才使用 Fork。
5. 暂停原任务的写入职责，确认共享 worktree 只有一个写入者。

不要在模型正在流式输出、工具正在执行或文件正在写入时切换 provider。

### 切换后兼容探针

不要只发送“你好”。应在一个可丢弃的干净测试任务里执行两轮只读测试：

第一轮：

```text
这是 provider 兼容性测试。请执行一次本地只读检查，报告当前工作目录名称，不修改任何文件，然后回复 READY-1。
```

第二轮：

```text
请引用上一轮报告的目录名称，并回复 READY-2；不要再次调用工具。
```

只有两轮都成功，才能证明该账号至少支持当前 Codex 的 Responses、多轮历史和基础工具调用。

### 新任务接管

1. 新任务进入原项目目录。
2. 读取项目实际采用的状态记录或交接快照；只有该项目确实使用三文件方案时，才读取那三个检查点文件。
3. 检查 `git status --short` 和 `git diff`。
4. 复述当前目标、已完成项、未完成项和下一步。
5. 确认旧任务已经停止写入后，再继续修改。

任务 Fork 只在操作者明确要求继承已完成聊天历史时使用；项目状态记录和交接快照才是跨账号接续的主要依据。

## 六、401、404、502、503、504 快速处置表

| 错误 | 常见含义 | 第一检查项 | 是否重试 | 停止条件 |
| --- | --- | --- | --- | --- |
| `401` | 凭据、登录、授权或账号被上游拒绝 | 当前 provider、账号是否过期、切换是否真正生效 | 不要用同一凭据反复重试 | 修复凭据或切换账号 |
| `404` + `model is not supported by any configured account in this group` | 当前账号组没有支持该模型的账号，或模型映射错误 | 账号组、模型名、模型映射和套餐支持范围 | 不靠切换推理等级重试 | 修复模型映射、账号分组或改用已支持模型 |
| `502` | 本地代理无法从上游得到有效响应，或协议转换失败 | `cause`、`upstream_status`、是否出现字段/transform 错误 | 纯上游瞬时错误在无副作用时有限重试；结构化参数错误不重试 | 同时段探针和服务端日志已保存；按错误正文分流 |
| `503` | 上游维护、过载、熔断或暂时不可用 | 干净任务探针、provider 健康状态 | 退避后最多一次 | 探针仍失败则切 provider |
| `504` | 网关等待上游超时 | 工作区和外部系统是否已经产生副作用 | 仅在确认操作可幂等后重试一次 | 状态不明时先恢复现场，不直接重放 |

补充说明：额度或速率限制更常见的标准状态是 `429`，但第三方中转可能重新映射状态码，所以仍要以错误正文和供应商后台为准。

若 `502` 的 `cause`、`upstream_status` 和正文只指向上游 `5xx`，且没有 `encrypted_content`、字段转换或分页谱系错误，无副作用时可以有限重试或等待。需要换线路时，先在可丢弃的干净任务中验证备用线路；正式恢复优先在新任务中读取项目状态记录或交接快照，从已确认断点继续。只有核对上一轮副作用和跨 Provider 兼容性后，才考虑在原任务重放。不要因此迁移会话、Fork 任务或删除密文。`502` 暂时消失不能证明线路已永久修复。

若正文包含 `invalid paginated history lineage` 或 `cutoff byte offset is past the source rollout`，应转为本地分页谱系排查。旧迁移回滚只可能修复这类由父会话被改短造成的问题，不能修复纯上游 `502`。

## 七、固定探针与分流方法

### P1～P5 的可复现测试矩阵

P1～P5 是本案例自定义的稳定性测试，不是 Codex 或 CC Switch 官方测试名称。测试目标和最小要求如下：

| 测试 | 验证目标 | 最小要求 |
| --- | --- | --- |
| P1 | 基础文本请求 | 不调用工具，只返回固定文本 |
| P2 | 较长输入和输出 | 处理一段虚构长材料，输出约 700～1000 字结构化分析 |
| P3 | 连续工具调用 | 依次执行 3 次独立、本地、只读命令；每次拿到结果后再继续 |
| P4 | 工具结果后的下一轮 | 不再调用工具，根据 P3 已有结果返回固定核对文本 |
| P5 | 较长上下文下的工具续轮 | 保留 P1～P4 上下文，再依次执行 3 次独立、本地、只读命令 |

每个模型和推理档位使用一个全新的无上下文窗口，并在该窗口中从 P1 连续执行到 P5。不要把每个 P 分别放进新窗口，否则无法验证上下文累积和工具结果续轮。不同 Provider 做严格对照时，应保持模型、推理档位、提示词、窗口起始状态和测试时间尽量一致；任何未控制变量都要记录。

本案例的结果是：Provider A 的 Sol 高和极高均在各自单一窗口内连续完成 P1～P5。Provider B 的 Astra 高在 5 个分别新建的窗口中执行 P1～P5，每项都有完整输出；这能证明各类请求可以分别执行，但因为 P4 没有继承 P3 的真实工具结果、P5 也没有积累 P1～P4 的真实上下文，不能把它记为完整的连续上下文测试。Provider A 的 Astra 在基础请求阶段即以明确的模型不支持 404 失败，因此无需继续测试其他推理档位。

### 真实 502 发生后的同时段三点对照

真实任务再次出现纯上游 502 时，优先在较短时间内完成：

1. 同一 Provider、干净窗口：固定文本探针。
2. 同一 Provider、干净窗口：一次本地只读工具调用，等待工具结果后的模型续轮。
3. 原任务窗口：固定文本探针。

若有独立 Provider，再用相同模型和提示词重复前两项。备用 Provider 必须尽量来自不同账号组或上游；否则只能证明另一个本地配置标签可用，不能构成独立对照。

### 如何解释结果

原任务连续失败两次后，不再原地重试，执行以下判断：

```text
同一 Provider 的干净探针也失败？
│
├─ 是 → Provider / 账号组 / 网络 / 代理链路范围
│      ├─ 独立 Provider 成功：优先查原 Provider 的账号池和上游
│      └─ 独立 Provider 也失败：再查本机网络、CC Switch 与共同上游
│
└─ 否 → 原任务固定文本探针是否失败？
       ├─ 是 → 原线程历史、compaction 或请求组装嫌疑上升
       └─ 否 → 故障已经暂时恢复；无法仅凭客户端确定根因
              ├─ 原复杂任务仍失败：检查负载、请求体和工具续轮差异
              └─ 原复杂任务成功：记录为间歇故障，等待服务端日志
```

探针用于缩小范围，不是根因证明。若探针开始时故障已经恢复，所有探针都成功也只能证明恢复后的状态，不能排除 Provider 短时不可用。

### 需要中转站核查的服务端证据

客户端完成对照后，应向中转站提供精确时间和时区、原始 Provider 标签、模型、完整错误正文，以及失败发生在工具调用前后哪个阶段。请中转站回查：

- 请求 ID、实际账号、账号组、调度节点和上游线路。
- 上游原始状态码与错误正文，是否被中转层统一映射为 502。
- 账号可用性、认证刷新、并发、速率、容量、排队和超时。
- `/responses` 的请求体大小、长上下文、工具结果续轮和协议转换。
- 重试次数、连接复用，以及同一时间前后的成功请求。

没有这些服务端证据时，客户端最多能判断故障范围，不能在账号池、节点、调度、认证或容量之间给出最终根因。

## 八、CC Switch 自动故障转移的正确使用方式

### 检查当前状态

启用前应只读确认当前 `enableFailoverToggle` 值，不要根据本文假设本机已经开启或关闭自动故障转移。检查过程不应修改 CC Switch 配置。

### 启用故障转移的前提

CC Switch 官方手册列出的前提包括：

1. 本地代理服务已启动。
2. Codex App Takeover 已启用。
3. 已配置 failover queue。
4. 已开启 auto failover。

备用队列中只应加入已经通过以下测试的 provider：

- 相同目标模型可用。
- Responses API 格式兼容。
- 两轮历史接续成功。
- reasoning item 可以继续。
- 基础工具调用成功。

### 推荐原则

- 初始最大重试次数建议为 1，避免同一工具请求被多次执行。
- 主 provider 放最稳定的账号，备用项按可靠性排序，不按余额多少排序。
- 定期查看 provider 健康、切换频率、熔断次数和失败原因。
- 不要把不同协议、不同模型映射但“碰巧能聊天”的中转混入自动切换队列。

自动故障转移能降低单 provider 暂时不可用造成的中断，但不能保证正在进行的流式回复无缝迁移，也不能修复已经损坏的 `encrypted_content` 历史。

## 九、恢复方法的优先级

遇到任务断联时，按风险从低到高使用以下方法：

1. 确认是否只是一次瞬时网络故障；无副作用时有限重试一次。
2. 用干净任务执行两轮兼容探针。
3. 创建干净任务，读取项目状态记录、交接快照和 Git 状态继续。
4. 只有操作者明确要求继承源任务的已完成聊天历史时，才使用 Fork。
5. 必要时先只读评估单个任务文件的备份与恢复条件，不直接修改真实会话。

本目录的 `TRB-004` 保存了历史迁移思路，`TRB-005` 记录了后来发现的分页谱系和回滚清单风险。当前真实安装与真实回滚入口都已暂停，不得把批量清理 `encrypted_content` 当作恢复步骤；只有相关入口通过独立安全审查后，才能重新评估真实使用。

## 十、发生 504 或断流时如何避免重复操作

504 只表示没有及时收到响应，不代表上游一定没有执行。

重试前必须检查：

- 文件是否已经创建或修改。
- Git diff 是否已经变化。
- 测试、构建或长命令是否仍在后台运行。
- 数据库写入是否已经发生。
- 是否已经发送消息、创建远端 Issue、提交 PR、发布或部署。

如果存在外部副作用或状态不明，应先恢复现场、确认幂等性，再决定是否重试。不能简单把同一提示再次发送给另一个账号。

恢复时使用下面的最短提示，避免把失败回合前已经完成的动作再做一遍：

```text
请先核对上一轮已实际完成的动作，仅从未完成断点继续，不重复创建、写入、发送或发布。
```

公开错误样例应使用 `<PROVIDER_NAME>`、`<MODEL_NAME>`、`<THREAD_ID>` 和 `<PORT>`，不得粘贴真实运行标识。

## 十一、需要保存的故障证据

以后遇到错误，至少在本地私有记录中保存以下信息：

- 出错时间。
- 任务名称和线程 ID；只限本地定位，不写入公开仓库或直接外发。
- 当前 provider 和模型名称。
- 完整错误正文，但删除 API Key、OAuth token 等秘密值。
- `cause` 和 `upstream_status`。
- 出错发生在回复前、流式过程中还是工具执行后。
- 干净两轮探针是否成功。
- 原任务连续重试次数。
- `git status --short` 和最近一次测试结果。

对外求助时使用脱敏任务别名和占位符，不发送真实线程 ID；优先提供精确时间与时区、原始 Provider 标签、模型、完整脱敏错误正文和中转站请求 ID。这些信息足以让后续 AI 或服务提供方判断故障层级，不必重新从所有配置开始调查。

## 十二、长任务推荐开场提示词

以后创建重要长任务时，可以在第一条消息中加入：

```text
这是一个可能跨账号、跨会话的长任务。

请先确认并沿用项目已有的状态或交接机制；如果项目没有可靠机制且任务确实较长，再建立最小状态记录：
1. 每完成一个阶段就更新目标、实际改动、验证结果、未完成项和下一步；
2. 在上下文压缩、账号切换或任务移交前立即写入检查点；
3. 同一 worktree 始终只允许一个任务写入；
4. 连续两次连接失败后停止原地重试，保留现场并从状态记录或交接快照恢复；只有我明确要求继承已完成聊天历史时才使用 Fork。
```

## 十三、不能彻底消除的风险

以下风险无法由本地设置完全消除：

- 第三方中转自身宕机、限流或协议实现不完整。
- 上游账号失效、额度耗尽或服务维护。
- 长连接经过系统代理、局域网或公网时被提前断开。
- 不同 provider 对 Responses reasoning、compaction 和工具调用的兼容差异。
- 504 后上游是否已经执行成功的不确定性。

能从根本上改善的是：不再让任务状态只存在于某个账号或某个聊天窗口中。即使发生断联，也能从项目状态记录或交接快照恢复；本地记录无法消除上游服务故障本身。
