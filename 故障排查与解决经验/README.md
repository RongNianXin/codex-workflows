## 先做这三件事

1. 保存完整错误正文、发生时间、产品版本和动作发生阶段；先脱敏，再分享。
2. 区分“没有显示”“不能继续”“请求失败”和“本地数据损坏”，不要按相似表象直接套用修复。
3. 涉及会话文件、数据库、账号、远端或重复发送时，先保留现场并确认已有副作用；不确定时停止写入。

## 目录规则

- 一级目录按故障层分类；每个公开故障使用稳定的 `TRB-xxx` 编号和独立资料夹。`TRB` 是 Troubleshooting Record（故障记录）的缩写，只用于唯一索引，不表示严重程度。
- 故障资料夹内的主记录文件按类型开头：HTTP 故障使用 `HTTP-<三位状态码>-TRB-<三位案例编号>-主题.md`，其他系统/协议签名使用 `ERR-...` 或 `SYS-...`；多个错误码按数字升序排列，没有明确错误码时不写入猜测。
- 主记录、调查过程、证据登记和配套工具都放在同一故障资料夹；工具状态与故障解决状态分开记录。
- 许可证或实现差异放在对应工具旁，不再散落在根目录。
- 没有可核验证据的内容留在被 Git 忽略的 `90-本地草稿/`；满足模板最低证据要求后才能进入公开索引。
- 路径可以调整，故障编号不得复用。合并案例时保留旧编号映射和迁移说明。

本目录于 2026-09-08 按上述规则完成首次统一整理。原来按临时问题名称建立的路径不再作为入口；旧文件内容仍可通过 Git 历史追溯，公开引用应改用稳定的 `TRB-xxx` 编号。

新增记录请复制[故障记录模板](故障记录模板.md)。英文维护者可使用 [English template](TROUBLESHOOTING_RECORD_TEMPLATE.md)。

## 维护流程

1. **收集**：记录一句话现象、错误签名、版本、时间和最小脱敏证据。
2. **分流**：建立或复用故障编号，区分已确认事实、合理推断和待确认项。
3. **验证**：先用副本、虚构数据或只读方式复现；记录失败尝试和停止条件。
4. **发布**：首屏明确当前是否解决、工具是否可用、最后核验日期和证据边界。
5. **维护**：产品版本、数据结构、配置或新证据变化时重验；过时条目标记“已失效”，保留仍有追溯价值的历史结论。
