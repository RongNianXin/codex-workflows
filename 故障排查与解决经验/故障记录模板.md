# 故障记录模板

复制本文件建立新记录。删掉说明文字后再公开；没有证据时保留为本地草稿，不要把猜测包装成解决方案。

命名约定：`TRB-xxx` 是稳定的故障记录编号（不是严重程度或错误码）。HTTP 故障文件使用 `HTTP-<三位状态码>-TRB-<三位案例编号>-主题.md`；其他系统/协议签名使用 `ERR-...` 或 `SYS-...`。多个错误码按数字升序排列，没有确认的错误码不要写入文件名。

| 字段 | 当前记录 |
| --- | --- |
| 故障编号 | `TRB-<三位编号>` |
| 解决状态 | **已解决 / 部分解决 / 未解决 / 已失效** |
| 工具状态 | 无工具 / 只读诊断 / 可用 / 已暂停 / 已废弃 |
| 最后核验 | `YYYY-MM-DD` |
| 证据边界 | 说明样本、平台、版本以及结论不能覆盖什么 |

> 安全第一步：写出用户现在首先应该做什么，以及哪些动作必须停止。

## 一句话现象

写清错误信息、用户可见表现和发生阶段。不要只写“不能用”。

## 当前是否解决

- 已解决：说明适用范围、验证结果和仍存在的限制。
- 部分解决：说明已验证的规避方法，以及尚未解决的部分。
- 未解决：必须明确写“当前没有已验证的解决方案”，再列排查进度。
- 已失效：说明失效原因和保留历史记录的价值。

## 已确认事实、合理推断与待确认项

### 已确认事实

只写有日志、代码、测试、官方资料或稳定复现支持的事实。

### 合理推断

写明推断依据和替代解释。

### 待确认项

列出会改变结论或解决方案的缺口。

## 排查过程

按顺序记录动作、目的、预期结果和实际结果。失败尝试也要保留，但说明为什么不再推荐。

## 解决或规避步骤

给普通用户最短安全路径。涉及写文件、数据库、远端、费用或不可逆动作时，写明前置条件、备份、停止条件和回滚。

## 配套工具

若有工具，将源码、测试、构建说明和可执行文件放在本故障目录内，并单独写明工具状态、支持平台、依赖、入口、哈希/构建来源和已知限制。工具状态改变时同步更新本记录和根目录索引。
