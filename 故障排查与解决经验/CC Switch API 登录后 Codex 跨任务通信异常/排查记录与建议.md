# CC Switch API 登录后 Codex 跨任务通信异常

测试日期：2026-09-07；成文日期：2026-09-08

## 问题表现

在 Codex 桌面端中，一个任务可以通过任务通信功能向另一个任务发送消息。正常情况下，目标任务会收到消息、生成回复，并在需要时把回执传回来源任务。

切换 CC Switch 的 API 登录线路后，曾出现以下现象：

- 发送接口显示成功，目标任务也出现了新回合，但回合没有可读内容；
- 目标任务没有按探针要求回复；
- 来源任务收不到跨任务回执，有时只会继续显示上一轮结果。

这里的“跨任务通信”特指 Codex 任务之间的消息发送与回执，不泛指浏览器窗口、普通聊天窗口或模型正常问答。

## 测试方法

测试使用同一来源任务和同一目标任务，不读取项目资料、不运行命令、不修改文件，也不执行业务。双阶段探针要求目标任务完成两步：

1. 在目标任务内回复 `DIAG_*_RECEIVED`；
2. 通过任务通信功能向来源任务回传 `DIAG_*_ACK`。

观察四个检查点：发送接口是否接受、目标任务是否创建回合、目标任务是否显示本地回复、来源任务是否收到回执。

## 实际测试结果

| 轮次 | 登录线路 | 探针要求 | 结果 |
| --- | --- | --- | --- |
| A | 中转线路 A | 只在目标任务回复 `DIAG_RECEIVED` | 消息在界面中可见，但目标任务没有按要求回复，反而沿用旧上下文继续处理原计划。未得到探针回执。 |
| B | 中转线路 B | 回复 `DIAG_B_RECEIVED`，再回传 `DIAG_B_ACK` | 两步都成功，跨任务链路闭环。来源任务收到了两次相同的 `DIAG_B_ACK`；现有证据无法区分是重复发送、平台重试还是重复投递。 |
| C-1 | 中转线路 A | 回复 `DIAG_C_RECEIVED`，再回传 `DIAG_C_ACK` | 发送接口返回成功，目标任务创建并结束了新回合，但回读内容为空；没有本地回复，也没有收到 ACK。 |
| C-2 | 官方登录 | 与 C-1 完全相同 | 目标窗口显示 `DIAG_C_RECEIVED`，来源任务收到 `DIAG_C_ACK`，两段链路全部通过。 |

C-1 与 C-2 使用同一条探针、同一目标任务。操作者确认没有改变模型选择、执行速度或推理等级，只切换了登录线路。这是本次最有价值的对照。

## 结论

1. 官方登录的跨任务通信在本次测试中正常。
2. 中转线路 B 在本次测试中能够完成跨任务通信，但出现过一次重复 ACK，稳定性仍需更多样本确认。
3. 中转线路 A 的异常能够复现。现有证据支持把问题定位为该线路与 Codex 跨任务消息链路的兼容性或稳定性问题。
4. 目前不能据此断定中转站“给模型注水”或替换了低智能模型。C-1 的回合没有可读消息或模型输出，故障更早发生在消息进入目标上下文或生成结果的环节。判断模型是否被替换，需要独立核对模型身份和同输入输出质量，不能用消息丢失代替这项证据。
5. B 轮收到两次相同 ACK，说明回执可能重复。它只算一次成功，不能当作两次独立测试。

这些结论来自少量受控探针，不代表相关线路在所有账号、模型、任务或时间段都一定成功或失败。

## 公开检索到的相似报告

目前没有找到与本案条件完全一致、证据链完整的公开帖子。找到的是 GitHub 和中文社区中的相似报告；作者背景和具体线路通常无法从页面确认，因此这里只按现象关联程度分类，不把它们当作本案的直接证明。

与本案最接近：

- [CC Switch #5792](https://github.com/farion1231/cc-switch/issues/5792)：第三方 Responses Provider 下，子任务收到空的可见 `NEW_TASK` 载荷；同一父任务使用官方 Provider 创建的子任务能够正常执行。它与本案的“消息被接受但目标没有取得可执行内容”非常接近。
- [CC Switch #7025](https://github.com/farion1231/cc-switch/issues/7025)：第三方 Responses Provider 下，Leader 向 Worker 发送跨任务消息后，目标线程出现持续错误；Issue 正文和评论包含中文复现及兼容性讨论。

相关但触发点不同：

- [CC Switch #4467](https://github.com/farion1231/cc-switch/issues/4467)：中文报告显示，切换到自定义 Provider 后，Codex 会话不再暴露 subagent 创建工具；它发生在子任务创建阶段，不能证明消息投递阶段存在同一故障。
- [OpenAI Codex #32165](https://github.com/openai/codex/issues/32165)：跨任务回合显示的权限状态与直接用户回合不一致，直接输入后行为恢复。它主要讨论权限上下文，不等同于 API 线路故障。
- [Linux.do：Codex 使用第三方线路时无法使用 subagent](https://linux.do/t/topic/2373402)：多名用户报告切换线路后同一上下文无法创建 subagent，并讨论了工具暴露、配置和加密参数等可能因素。它发生在创建或工具可用性阶段，不能直接证明消息已发送后出现的空回合或回执异常。

这些公开报告说明跨任务消息和第三方 Responses 兼容性确实有人遇到，但不能据此断定某个中转站一定替换模型或“降低智能度”。遇到类似现象时，可以按下文的唯一编号探针确认是发送、目标回合、目标回复还是回执环节出问题，再向对应项目提交最小复现信息。这样比直接发布账号、密钥或完整聊天记录更容易得到有效帮助。

## 使用建议

- 需要可靠跨任务协作时，优先使用官方登录。经过测试的中转线路可以用于低风险任务，但不要把一次成功当成长期保证。
- 每次切换 API 登录线路后，先运行一次只读双阶段探针。确认目标本地回复和来源 ACK 都出现，再发送正式任务。
- 每次探针使用唯一编号，例如 `DIAG_20260907_01`，避免旧回执和新回执混淆。
- 发送端应设置有限等待时间。发送接口返回成功只表示请求被接受，不能说明目标任务已经执行。
- 正式任务涉及写文件、Commit、远端操作或其他有副作用的动作时，如果没有明确回执，不要自动重发。先查询目标状态，避免消息延迟后造成重复执行。
- 收到重复 ACK 时按同一探针去重，并记录发生时间。不要把重复回执当成两次完成。
- 向中转站反馈时，提供发生时间、登录线路、探针文本、四个检查点的结果和空回合现象；不要提交 API Key、Cookie、账号凭据、真实任务 ID 或项目资料。

## 建议的最小探针

```text
【跨任务通信探针 <唯一编号>】这是只读测试，不是业务指令。请不要读取项目、执行命令或修改文件。

请先在本任务只回复一行：<唯一编号>_RECEIVED；随后通过任务通信功能向来源任务回传一行：<唯一编号>_ACK。每项只发送一次。
```

通过条件：目标任务显示 `<唯一编号>_RECEIVED`，来源任务收到且只收到一次 `<唯一编号>_ACK`。任何一步缺失，都应把该线路标为“跨任务通信待确认”，而不是继续正式任务。
