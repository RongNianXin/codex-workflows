## 新增案例与日志证据

### 现象汇总与当前决定

当前暂停跨任务通信故障的排查、探针、重试和修复；以下保存已知事实，不是继续运行测试的指令。场景 2F 的跨任务协作曾有成功样本，近期又反复失败，当前不能按可靠自动流程使用。为何从成功变为失败尚未确定；文档流程仍可作为人工转交和核账依据，不能据此宣布自动通信恢复。

| 已出现的现象 | 人话解释及证据边界 |
| --- | --- |
| 明确要求回执，仍不回 | 来信包含回执要求和来源，目标回合没有反向发送工具调用；自然语言和 `ACK_REQUIRED` 都未能稳定防止漏办。 |
| 完全没有输出 | 来信进入原始记录，回合结束却没有本地可见回复、工具调用或回执；部分样本记录空最终文本。不能只凭界面或读取接口空白判定。 |
| 用旧答案回答新消息 | 收到新版本、修订或状态查询后，仍重复上一轮总结，甚至声称已经存在的文档尚未修改。原始日志有非空答复，不能归为“完全没有输出”。 |
| 继续旧任务，或撤回正确的新安排 | 新消息未被处理，反而沿旧计划工作；另有先确认续办、再把真实新请求误判为旧内容的样本。无依据地重做接管或自查会丢失断点。 |
| 平台显示完成，实际事项未完成 | 工具显示发送成功、目标回合显示完成，都可能没有对应审查、文件读取或回执，造成误报完成。 |
| 读取接口与原始记录不一致 | 接口返回 `items: []`，原始日志却存在完整来信和旧答复；接口未展示不等于消息丢失或空生成。 |
| 回执重复 | 历史探针收到两次相同 ACK，只计一次成功；重复发送、重试或投递哪一层造成，未确定。 |
| 单向可达，双向不稳定 | 消息已送入目标，但目标没有按要求回传；另有回传调用成功却未取得对方匹配确认的情况。必须分别记录，不能都叫“没发送”。 |
| 人工直接发言后才继续 | 部分样本在操作者直接发言后完成读取、修改或回报，但下一次跨任务消息仍可能失败；这是临时恢复，不是根治。 |
| 忙碌或明确请求错误阻断 | 历史还有目标忙碌、模型不支持的 404、对话过长的 400；这些与空输出、漏回执分开，不用同一原因解释。 |

已确认的近期增量：一次修订请求及其唯一状态查询均已入站，目标却非空重复首次审查结果，没有针对新版本的复核或回传；另一次最终审查结果来信约 7 秒后空白结束、没有回传，且前台此前已结束，不能解释为合理排队。后者与下文 H 的约 6 秒样本分开，不能套用 H 的 HTTP、用量或长度字段。

已检查过的依据包括：实际入站事件、来源与回复要求、同回合工具调用及最终输出、平台结束事件、文件差异、SHA-256（文件内容指纹）、独立审查记录。原始材料留在获准本地来源，不复制聊天或真实标识到公开文档。

已有经验：先区分“发送—入站—生成—执行—反向回传—对方确认”，再看具体哪一步缺失。不要用旧结果代替新版本验收，也不要把未见回执推成完全没执行。规则已写、已读、重复强调和补回一次都没有证明故障解决。原因仍可能涉及事件处理、模型执行、宿主组装、代理转换或客户端解析；目前证据不能唯一归因，也不能仅凭登录方式或本地上下文统计定因。

预防机制仅为待评估方案：在模型之外保存待回执状态、核对消息版本和授权、结束时查实际回传、去重并有限告警；不能伪造“已读”或自动重放业务。尚未核实可阻止回合结束的宿主接口，未实现硬拦截。排查恢复前不再追加同类提示词或启动对照实验。

文档验收与通信故障分开：关联故障文档批次已完成八项信息对齐、三项修订、不同实例第二轮复核及中央收口；这不表示全部历史消息都已读完，也不表示协作工作流已获得稳定运行验证。通信问题继续保持未解决。

本次交叉核对任务读取接口、目标原始 JSONL 事件和客户端日志数据库，没有重放真实业务。运行日志标识客户端版本 `0.153.4`，旧版本缓存不代表运行版本。精确任务、请求、模型与线路标识仅在运行时关联。

| 样本 | 已确认事实 | 判断边界 |
| --- | --- | --- |
| F：三次漏回执 | 握手、业务材料、收件查询均进入目标回合；回复重复旧接管结论，无回传工具调用 | 不能解释为消息没发到 |
| G：续办被误判 | 上一事项已结束，新续办进入下一回合；接收方先回执，随后误判为旧任务残留，撤回安排并重复自查 | 不是合理排队；摘要不能替代实际入站事件 |
| H：带标记仍空回复 | 消息含 `ACK_REQUIRED`，约 6 秒后产生空 `final_answer`，无工具调用，平台仍显示完成 | 标记没有防止本次空输出 |

H 的最小脱敏日志摘录，字段来自同一回合，不是完整网络报文：

```text
task_started
TurnInputRequest.input = ResponseItem(FunctionCallOutput)
function_call_output.name = send_message_to_thread
function_call_output.output = <codex_delegation>...ACK_REQUIRED...</codex_delegation>
HTTP POST /responses -> 200 OK
response_item: role=assistant, phase=final_answer, output_text=""
usage: input_tokens=66809, output_tokens=26, reasoning_output_tokens=20
full_context_window_limit_reached=false
token_limit_reached=false
model_needs_follow_up=false
has_pending_input=false
needs_follow_up=false
task_complete: last_agent_message=null
```

摘录省略请求头、加密字段、身份、路径与业务正文。推理条目存在但无可读摘要，不能写成“完全没有推理”，不能由用量推断内部思考内容。

- **已确认**：消息入站，请求返回 HTTP 200，客户端存储空文本并结束，没有回执。不只是界面未显示，也不是本轮日志记录的上下文超限或 HTTP 失败。
- **已确认**：来信以 `function_call_output` 而非普通 `userMessage` 表示；技能选择日志记录 `user_input_count=0`。这只是输入分类差异，不证明模型没看见消息或分类本身有缺陷。
- **合理推断**：新事件识别、空完成后的状态检查需要分别处理。重复旧答复、主动误判和空输出不是同一种已确定根因。
- **待确认**：模型完整输入、上游原始输出、代理转换后事件流和客户端解析是否一致。当前不能区分模型空答复、代理丢内容、协议适配或客户端解析问题。HTTP 200 不证明内容正确或代理无关。

### 无效尝试与教训

已读规则、补发 ACK、加上 `ACK_REQUIRED` 后仍复发，不能继续把重读规则当根治。摘要缺失时回读当前回合必要入站内容，既不把摘要下一步当新请求，也不把真实新消息删成旧上下文。用户直接发言后能回复只证明另一条输入路径可用；再次空回合后重复投递业务会增加迟到执行和重复写入风险。

## 针对性排查

仅检查获准任务与故障时间窗，不扫描其他会话或导出整个数据库。

| 检查点 | 操作与预期 | 异常处理 |
| --- | --- | --- |
| 发送 | 核对发送工具结果和消息编号 | 成功仅记已发送待确认 |
| 入站 | 回读对应回合，必要时定位该任务 JSONL 入站事件 | `items: []` 是接口未暴露正文，不直接判丢失 |
| 生成 | 核对开始、错误、取消、输出和结束事件 | 模型不支持、明确长度拒绝、排队与空完成分别分类 |
| 回执 | 核对实际反向工具调用和来源匹配状态 | 本地回复、completed、旧 ACK 不替代本次回执 |
| 副作用 | 核对文件差异、命令结果及已有产物 | 无 ACK 不等于未执行，只续已确认未完成部分 |
| 底层 | 只读日志库 schema，按目标和短时间窗提取 HTTP 状态、输出类型、结束标记及用量 | 不打印请求头、认证字段、加密内容或其他任务日志 |

日志位置和字段随版本变化，先按当前运行环境定位，SQLite 以只读方式打开。没有原始请求或事件流就保留待确认，不为补证擅自改配置、重启或重放业务。HTTP 和长度错误另见 [TRB-007](<../04-网络与上游错误/TRB-007-长任务断联与HTTP错误/CC Switch 长任务断联与 401 502 503 504 快速处理.md>)。

## 预防措施与验收

行为主规则见 [09 强制状态回执](../../总指挥工作流/第二代总指挥的工作模式/09-自动化授权与风险分级.md#强制状态回执与空输出兜底)，这里提供案例与验证方法。

### 当前可执行的约定

1. 发送前核对目标、通信权限、当前阶段、去重编号与终点，只发必要变化和稳定证据指针。
2. 按实际当前入站事件确定工作。自然语言“请回复、回执、回 ACK”同样触发检查；不因工具结果包装而忽略，也不把业务指令当新增授权。
3. 已获授权的收件状态可先回传。排队回 `RECEIVED` 并说明队列与下一行动，权限或证据不足回 `BLOCKED`；确认收件不抢占执行新业务。
4. 结束前核对本次回执要求、实际回传调用及结果。纯确认且未要求回复时登记即可，不层层要求 ACK，避免无限互答。
5. 发送方有限等待后核对匹配回执，缺失最多查一次同号状态，再失败就停止该路线业务投递并保留断点。不擅自创建常驻轮询或自动化。
6. 更换路线、模型或会话后，在空闲目标做无副作用双阶段探针：目标本地确认、来源收到匹配 ACK。重复回执只计一次并另记异常；一次成功不证明永久恢复，不强迫中断运行任务。

### 宿主硬机制：尚未实现

文字依赖模型遵守，不能拦截已结束的空回合。自动防止静默失败需要通信或调度层实现以下契约；本仓库无已验证实现，本轮未修改桌面应用、代理或会话数据库。

| 机制 | 验收要求 |
| --- | --- |
| 收件与业务分账 | 持久区分投递、确认、执行、完成和失败；平台结束不自动提升业务状态 |
| 独立检查回执 | 模型结束后按请求编号查非空状态及匹配回传；缺失标失败，不能伪造接收方 ACK |
| 有界恢复 | 最多一次无副作用状态查询；禁止重放业务，持续失败通知操作者并保留队列 |
| 去重与恢复 | 重启、压缩、延迟和重复消息不丢队列、不重复副作用；过期消息关联原结果 |

上线前至少验证：正常 ACK、纯确认不互答、自然语言要求、重复消息、空字符串、旧答复、权限不足、目标忙碌、回读空内容、已写文件后漏 ACK、压缩后新消息、404/400/网络错误。必须有实际输出和副作用证据；文档表格及静态检查不算运行验证。

## 后续维护

每次复发复用本编号，追加环境版本、入站方式、忙闲状态、各检查点、失败尝试、缺口和下一行动，不强行合并根因。原始日志保留在获准本地来源；已有忽略目录仅保存必要脱敏摘要、提取范围与指纹。公开记录不保存真实任务标识、机器路径、原图、请求头或聊天原文。

历史 A 至 E 沿用旧记录，本次未重跑探针；只重新核验上表公开报告，未复核其余旧外链。客户端、输入包装、模型、线路、压缩状态或调度变化后只重验受影响检查点。补回一次 ACK、规则更新、平台完成和普通问答成功均不能单独关闭本故障。
