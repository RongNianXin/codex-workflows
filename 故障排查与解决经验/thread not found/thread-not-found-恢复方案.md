# Codex `thread not found` 恢复方案

## 现象

- 某个原本可以正常对话的 Codex 任务突然报错：`thread not found: <THREAD_ID>`。
- 故障发生前，该任务的最后一轮执行被中断。
- 原任务记录仍存在，并非聊天内容已经被删除。

## 本次确认到的事实

1. 使用报错中的 `<THREAD_ID>` 直接读取任务，读取成功。
2. 任务当时为 `notLoaded`，最后一轮为 `interrupted`。
3. 尝试取消归档时，应用返回“没有找到该任务的归档记录”，因此本次故障不能确认为单纯误归档。
4. 向原任务 ID 发送一条最小验证消息后，任务成功完成新一轮回复，状态恢复为 `idle`。
5. 再导航回原任务，页面恢复正常。

## 成功恢复步骤

在另一个正常工作的 Codex 任务中执行：

1. 用报错里的 `<THREAD_ID>` 读取原任务，确认任务记录仍存在。
2. 检查是否被归档；若确实归档，则先取消归档。
3. 向原任务发送一条不会触发业务操作的验证消息，例如：

   ```text
   连接恢复验证：不要读取文件、不要调用工具、不要继续任何旧工作，只回复“线程已恢复，可以正常对话”。
   ```

4. 等待该轮完成，确认：
   - 没有错误；
   - 任务状态为 `idle`；
   - 收到预期回复。
5. 让 Codex 将应用界面导航回原任务，再继续正常对话。

## 本次结论

本次问题不是任务真正丢失，而是任务在中断后处于未加载状态，原页面继续引用该任务时发生异常。直接按任务 ID 发送一条最小消息，使任务重新加载并完成一轮执行，是本次实际验证成功的恢复动作。

> “原页面引用失效”属于基于现象的推断；应用内部根因尚无官方说明。

## 复发时的处理顺序

1. 不要删除原任务，也不要立即清理 Codex 本地数据。
2. 先复制报错中的任务 ID。
3. 新建一个临时排障任务，请它按上述步骤检查并唤醒原任务。
4. 若读取原任务也返回 `thread not found`，再检查侧边栏筛选和“设置 → 已归档任务”。
5. 若任务记录仍不可读，保留完整报错与发生时间，再按官方排障渠道反馈；不要自行修改本地任务数据库。

## 官方参考
